# Cross-engine hook registry and router

Status: design proposal. No implementation exists yet. This document
recommends building the registry/router inside houston, incrementally,
starting with aeye.

## 1. Problem statement

Three agent engines run on this machine — Claude Code, Codex, Cursor — and
each declares hooks (pre/post-tool guards, session lifecycle notifications,
status updates) in its own native config format. Four repos independently
wire behavior into those formats: aeye, lazytmux, dispatcher, and nix-config
itself. Because there is no shared registration point, the same *behavior*
gets declared, and usually re-implemented, once per engine.

The clearest case is aeye. Five behaviors — `images.sh`, `diagrams.sh`,
`session-reset.sh`, `session-backfill.sh`, `diagram-guidance.sh` — are
declared three times, in `adapters/claude-code/plugin/hooks/hooks.json`,
`adapters/codex/plugin/hooks/hooks.json`, and `adapters/cursor/hooks.json`,
differing only in event-name casing and how the plugin root is spelled
(`${CLAUDE_PLUGIN_ROOT}` vs `$PLUGIN_ROOT` vs `<ADAPTER_DIR>`). Re-verification
during this design pass corrects the picture in both directions. Three of the
five are genuinely drifted logic, not cosmetic copies: `diagrams.sh` differs
by 231 changed lines between the claude-code and codex adapters (not 229),
`session-backfill.sh` by 152 (not 150), `images.sh` by 58 (not 56) — different
session-id extraction, different path resolution. But `diagram-guidance.sh` is
byte-identical across claude-code and codex; it isn't drifted at all, and
Cursor's `session-backfill.sh` is a deliberate 6-line no-op stub, not a
degraded copy, so diffing it against the other two overstates drift. Against
that, two files outside the original five-item list turn out to be drifted
too: `session-reset.sh` (21 changed lines) and each adapter's own
`lib/shim.sh` (61 changed lines, codex vs cursor). aeye already has one piece
of shared-code machinery — a `justfile` `sync-{codex,cursor}-core` step that
vendors two core files via `cp` — which is evidence the maintainer has already
felt this pain, not evidence the problem is solved. Net effect of the
correction: aeye still has real, multi-file, multi-engine drift; it is not
weaker than originally believed, it is differently shaped.

The other repos show the same pattern at smaller scale. lazytmux declares 14
events / 23 hook entries for Claude Code via a plugin `hooks.json`, and
separately injects hook content into `~/.codex/config.toml` and
`~/.cursor/hooks.json` straight from its Nix home-manager module — using two
different injection mechanisms because Codex's `config.toml` can carry
substantial hand-edited content (so lazytmux appends via a marker-guarded
`sed`/heredoc rather than templating the whole file), while Cursor's
`hooks.json` is merged in via `jq` with marker-scoped strip and `jq empty`
validation before write. dispatcher declares one `SessionEnd` hook for Claude
Code and one for Codex — but has **no Cursor hook mechanism at all**, unlike
lazytmux. Its two `dispatch-notify.sh` copies are byte-identical, generated by
`scripts/gen-adapters.sh` from a single `adapters/core/dispatch-notify.sh`; the
duplication is a build artifact, not organic drift, though nothing enforces
re-running the generator, so it can silently drift the moment someone hand-edits
one copy.

nix-config already contains the seed of the right idea, and its current shape
is itself evidence for what this design should not repeat. `home/ai/agent-hooks/`
holds exactly four guard binaries (`git-default-branch-guard`,
`nix-stage-guard`, `git-commit-autostage-guard`, `secret-read-guard`) that are
already engine-neutral in the sense that matters: they speak Claude Code's
PreToolUse contract (JSON on stdin, a decision on stdout, silence = abstain),
confirmed verbatim from the module's own header comment. `home/ai/pi/hook-bridge.ts`
already treats that contract as a wire protocol worth reusing — it shells out
to three of the four guards (not `secret-read-guard`, which isn't wired for
pi) via `execFile` with a 5s timeout, consolidates with deny-wins, and treats
malformed or empty output as abstain. That is a small, working preview of
exactly the router this document specifies, built once, for one non-native
caller. But `home/ai/codex/default.nix` never touches `agent-hooks` at all —
confirmed directly on this machine: `~/.codex/config.toml`'s actual hook
content today is entirely lazytmux-managed (two marker-guarded blocks,
"codex resume-on-restore" and "codex status-line hooks") with **zero aeye
content**, contradicting an earlier draft of this evidence. Codex has no path
to the shared guards today; that gap is real even though the earlier evidence
for it was wrong. And `home/ai/cursor/default.nix` writes `~/.cursor/hooks.json`
via **three independent jq merge scripts** — aeye's `install.sh`, an inline
dispatcher-stop block, and lazytmux's `cursor-hooks-install.sh` — each
hand-rolling its own marker-strip-and-validate merge, with no shared code
between them. Three independent implementations of "safely merge one more
entry into a JSON file without clobbering the others" is the clearest single
piece of evidence that the current model — every repo owns its own writer, in
every engine's format, from scratch — does not scale past four repos, let
alone the fifth and sixth that will eventually want a guard.

Finally, houston already implements half of the relevant pattern for one
engine, and getting this right depends on being precise about which half.
`hook/hook.go`'s `Dispatch` reads Claude Code's stdin JSON, merges it into a
per-session state file, and returns only `error`/`nil` — it never writes
anything to stdout and never invokes a guard. `main.go`'s `cmdHook` always
returns exit 0 regardless of that error ("Never fail loudly from a hook —
Claude Code would surface the error to the user"). `hook/install.go`
self-installs into `~/.claude/settings.json` with `timeout: 5` per entry and
**no matcher** — it runs alongside whatever guards are already registered, it
does not compete with them. `runs/hooksource.go` plus `runs/registry.go`
already compose a layered `Registry` (sources `tmux`, `crew`, `hooks`, fixed
precedence, `Delta`-keyed) exposed over `/api/runs` and `/api/runs/stream`
(SSE), already consumed by the frontend (`useRuns.ts`, `RunCard.tsx`). Hook
dispatch and the web server are the same binary, decoupled through the
state-dir files, so dispatch works with no server running. The accurate
split, and the one this design is built on: **ingestion (stdin → state write)
and live view (Registry → SSE → frontend) already exist and generalize
cleanly to more engines. The verdict/decision path — consuming several guard
results and rendering one native-shaped allow/deny/ask response, which is
hard constraint 1 — does not exist anywhere in houston today.** It is new
work regardless of where it is built.

## 2. Prior art evaluated

### HookBus

[HookBus](https://hookbus.com) (`github.com/agentic-thinking/hookbus`) is
this exact design, already built and self-hosted: a daemon that publishers
push lifecycle events into, where subscribers return allow/deny/ask, sync
subscribers block the caller and async ones only observe. It is the reference
implementation of a separate spec repo, `agentic-thinking/agenthook`. The
facts below were checked directly against the GitHub API, hookbus.com, and
the project's `NOTICE` file, not taken on faith from an earlier draft.

| Fact | Value |
|---|---|
| Core license | Apache-2.0 (Python) |
| Publisher licenses | MIT, stated — but the Claude Code publisher's actual GitHub license metadata is `NOASSERTION`, not MIT; a minor inconsistency worth a footnote, not a blocker |
| Publishers shipped | Claude Code (Python), Codex (JavaScript), OpenCode (JavaScript), Amp (TypeScript) |
| Cursor publisher | **Does not exist.** hookbus.com lists it as "coming soon"; the linked page 404s |
| Core stars | 2 |
| Publisher stars | 0, each |
| Last activity | publishers untouched since May 2026; core last pushed June 2026 |
| Self-description | README describes it as suitable for "development, evaluation, and controlled pilots" |
| Commercial tier | hookbus.com sells a paid Enterprise tier alongside the open-source core |

Two facts matter more than the star count. First, performance: this user's
own process-startup measurements put a bash script at ~2.2ms, bare `python3`
at ~14.5ms, and `python3` importing `json`+`urllib` at ~39ms. HookBus's Claude
Code publisher is a per-event Python subprocess doing exactly that import, so
its ~39ms floor sits on the critical path of every tool call, before any
handler even runs. A freshly built and timed comparison — this repo's own
`houston hook <event>` binary, JSON-on-stdin to state-write, end-to-end —
averages **2.35ms over 30 runs**, on par with the bash floor and roughly 17x
cheaper than HookBus's measured Python floor. That is direct evidence for §4
below: a compiled binary is already cheap enough to stay on the critical path
per event, with no daemon required.

Second, the `NOTICE` file discloses a pending UK patent application,
**GB2608069.7**, filed April 2026, claiming a governance-aware lifecycle event
bus with **priority-weighted deny-wins consolidation**, circuit breakers, and
failover/merge groups. Apache-2.0 §3 grants a patent license for the project's
code *as distributed*; it does not extend to an independent reimplementation.
It is a filed application, not a granted patent, and UK claims do not publish
until roughly late 2027, so there is nothing to infringe or design around in
a legal sense today. It is a factor to name, not a blocker.

Naming it plainly: recommending an independent build, rather than adopting
HookBus's own code, means this design forgoes the Apache-2.0 §3 patent
license grant entirely — that grant only ever covered *their* code as
distributed, and an independent implementation was never inside it regardless
of what this document recommends. That trade is acceptable specifically
because §2's verdict already rejects HookBus on its technical and maturity
merits alone (the Python subprocess floor, the missing Cursor publisher, the
"evaluation and pilots" maturity), not because of the patent — the grant
being unavailable to an independent build isn't a new cost this
recommendation introduces, it's a fact about a path already ruled out on
other grounds. It is also the reason this document, and the design it
specifies, never uses the phrase "priority-weighted" and never describes
consolidation in the claim's own vocabulary. §4 below defines an independent,
much simpler rule (plain deny-wins: any deny wins, full stop) that happens to
be the natural choice for the four-guard case this machine actually has, not
a paraphrase of someone else's pending claim.

**Verdict: do not adopt or wrap HookBus.** The combination of a Python
subprocess floor on the tool-call critical path, single-digit-star maturity
that the project itself scopes to "evaluation and pilots," no Cursor
publisher (a real, current gap for a user who dispatches work to Cursor
workers), and a Nix-first, static-binary stack that already has a
cheaper, already-built answer in houston, rules it out on the merits alone —
independent of the patent question.

### Everything else

`@agiflowai/hooks-adapter` is a real, actively published npm package doing
payload normalization across agent hook formats. It is not adopted here, but
it is evidence that the schema question in §7 is a shared, recognized problem
and not a houston-specific one — this design's normalized envelope is solving
a problem other people are independently solving too, which is a point in its
favor, not a novelty claim. `weykon/agent-hooks` is a Rust trait for unified
*registration* across several agent CLIs; it is closer to a language-level
interface than a bus, and it doesn't touch the router/consolidation problem
this design needs solved. Neither changes the recommendation in §3.

## 3. Recommendation: build it in houston

**Build the registry and router inside houston, as a generalization of code
that already exists there. Do not create a new repo. Do not put it in
nix-config.**

The reasoning follows directly from the problem statement's last paragraph:
houston already owns the ingestion half (a per-event exec CLI that decodes an
engine's hook payload and writes state) and the live-view half (a layered
`Registry`, SSE, and a frontend that already renders it). The one piece that
does not exist anywhere — consuming several guard verdicts and rendering one
native-shaped response inside an engine's timeout — is new work no matter
where it is built. Building it in a new repo, or in nix-config, would not
avoid writing that new code; it would only add the cost of calling back into
houston's live-view half from somewhere else, or duplicating a second copy of
it. Building it in houston means the router's live-view tap (§6) is a
function call and a file write, not a network hop to a second service.

nix-config is the wrong home for the *logic*, but it remains exactly the
right home for the *wiring* — this already matches the existing pattern,
where each repo's own hook behavior ships as that repo's own binary or
script, referenced from a Nix module, rather than living inside nix-config
itself. The registry's binary lives in houston; the Nix modules that point
each engine's native config at that binary, and that declare which guards
from which repos are active, stay in nix-config, unchanged in shape from how
aeye's, lazytmux's, and dispatcher's own hook scripts are wired today.

This choice has a real cost, and it should be named rather than elided: aeye,
lazytmux, and dispatcher's hook wiring would come to depend on a houston
binary being present and correct on the machine. That is the same
dependency-direction cost a standalone new repo would also introduce — three
repos would depend on *something* that isn't themselves — just shaped
differently. Putting that something inside houston rather than a new project
means it inherits an existing release/build/test pipeline instead of needing
a new one, and it means the live-view tap is free instead of a second
integration to build.

## 4. Router shape: per-event exec, no daemon

**The router is a subcommand of the existing static Go binary, exec'd once
per hook event by the engine's own native hook mechanism. There is no
long-running daemon.**

This is a direct reading of hard constraint 4 (Nix-first: a static binary
fits this stack; a Docker daemon does not) combined with the measurement in
§2: houston's own binary already completes a full stdin-to-state-write cycle
in 2.35ms average, in the same class as a bare bash script and roughly 17x
faster than HookBus's Python floor. A daemon would trade that away for
socket-management, liveness-probing, and restart-on-crash complexity in
exchange for avoiding a process-start cost that is already negligible. There
is no daemon-shaped problem here to justify the daemon-shaped solution.

### What "the router can deny" actually means, per engine

Claude Code's own documentation states plainly that "all matching hooks run
in parallel" — native multi-hook fan-out for one event is confirmed, not
assumed. What the docs do **not** state is how differing verdicts from those
parallel hooks are consolidated when they disagree (one allow, one deny) —
that is inference from the exit-code-2 "blocking error" language, not a
documented rule, and it was not checked at all for Codex or Cursor. This
design does not borrow an unverified native rule. It states its own:

> **Consolidation rule: plain deny-wins.** Collect every handler's verdict
> for one event. Ignore `abstain` (it is the identity element — a handler
> that abstains behaves as though it never ran). If any handler returns
> `deny`, the consolidated verdict is `deny`. Otherwise, if any handler
> returns `ask`, the consolidated verdict is `ask`. Otherwise `allow`.

This already matches the two things that exist today: the pi bridge's
deny-wins fan-out over three guards, and the guards' own silence-is-abstain
convention. It needs no priority weights because there is nothing to weigh —
every handler's opinion counts equally, and a single deny is decisive by
design, which is the correct default for a security control.

Whether an engine can act on a `deny` at all is a separate, and separately
verified, question per engine:

| Engine | Confirmed deny path | Evidence |
|---|---|---|
| Claude Code | Yes | Docs state PreToolUse hooks can block via `hookSpecificOutput.permissionDecision`; parallel fan-out confirmed above |
| Codex | **Not confirmed** | The only Codex hooks deployed on this machine today (lazytmux's status/resume hooks, dispatcher's `SessionEnd` notifier) are fire-and-forget, with no observed deny path in any of them |
| Cursor | Partially confirmed | Cursor's hook protocol returns a decision via a `permission` field (named in this design's own required content); the exact set of values it accepts (binary allow/deny, or tri-state with ask) was not confirmed against Cursor's own docs during this pass |

The design's answer for an engine that turns out to be observe-only:
**handlers still run and their verdicts still reach the live-view tap and
the router's own logs; the router simply never asserts a deny in a shape the
engine can enforce.** For Codex specifically, until its deny path is
independently confirmed, the registry treats Codex's `pre_tool` event as
**observe-only** — guards run, a would-have-denied verdict is visible in
houston's panel and in logs, but no tool call is actually blocked on Codex.
This is safer than assuming a deny path exists and silently no-op'ing it
(which would give a false sense of protection); it is listed again in §11 as
something to verify before Codex guards are treated as enforcing.

### The timeout budget chain

There is no single deployed timeout today to inherit: lazytmux's Codex
entries set `timeout = 30`, its Cursor entries set 15, 30, or 60 depending on
the hook, houston's own installer sets 5, and dispatcher's Codex plugin sets
none at all (falling back to whatever Codex's own unstated default is).
Citing that range would answer the wrong question anyway: constraint 1 is
about the timeout the *registry itself emits* when it writes native config
(§8), because that is the number the router has to live inside, not whatever
happens to be deployed today. This design fixes one chain, emitted the same
way for every engine, rather than inheriting per-engine values that vary for
reasons unrelated to what the router actually needs:

| Layer | Budget | Rationale |
|---|---|---|
| Emitted timeout (native config, §8) | **5s**, all three engines | Matches houston's own existing convention (`hook/install.go` already emits `timeout: 5`); deliberately tighter than lazytmux's 15–60s Cursor values or Codex's 30s, because those exist for fire-and-forget status hooks, and this entry is now on the synchronous deny path, where "I don't care how long it takes" is no longer true |
| Router's internal deadline | **4.5s** | 500ms margin under the emitted timeout, covering the router process's own start plus forking N handler subprocesses. The 2.35ms figure was measured for `houston hook <event>`'s stdin-to-state-write path specifically, not for guard fan-out (forking N bash+`jq` subprocesses and consolidating), which hasn't been separately measured — the 500ms margin is generous against either number, so this doesn't change the recommendation, but the two shouldn't be conflated as the same measurement |
| Per-handler sub-budget | **4.3s**, shared context, run concurrently | Handlers run as parallel goroutines under one deadline context, not sequentially, so the sub-budget is the router's internal deadline minus a small (~200ms) consolidation margin — time the router needs, after the slowest handler returns or is killed, to build and print the one consolidated response |
| Engine default when no timeout is declared | **Unverified** | Dispatcher's Codex plugin declares no timeout today; Codex's actual fallback was not confirmed during this pass — see §11 |

The real addition this router makes over what exists piecemeal today is
cross-engine reuse of the same guard binaries — Codex currently has no path
to `agent-hooks` at all — plus one normalized side-channel into houston's
registry, instead of each engine's hooks writing state (or nothing) on their
own.

## 5. Failure mode

Hard constraint 3 asks for a stated decision, not a default. This design
makes two, at two different layers, and they are not the same decision:

**A single guard erroring or timing out already abstains, and that stays.**
This is already true in two places today: the pi bridge treats malformed or
empty guard output as abstain, and `main.go`'s `cmdHook` — the "never fail
loudly" comment lives there, not in `hook.go` — always exits 0 regardless of
what `Dispatch` returns. One flaky guard should not be able to block every
tool call it's wired to; abstain is the correct behavior for a single
handler's failure, and it costs nothing to keep.

**The router — the dispatch binary itself — being unreachable or crashing is
a separate failure, and this design's recommendation is fail-open: if the
binary can't be found, can't start, or can't produce a verdict before its
own deadline, the tool call proceeds as if no hook had fired at all.** The
trade-off is real and is named here rather than defaulted: fail-open means a
bug in the registry, or a machine where the binary went missing after a
botched Nix rebuild, silently disables every guard wired through it, with no
visible error at the point of the tool call. The alternative, fail-closed,
means the same bug or missing binary freezes every tool call on every agent
on the machine, on every engine, simultaneously, until someone notices and
fixes the infrastructure bug — not the code the guards are supposed to be
protecting. Given that this router sits in front of every guarded tool call
across three engines at once, the fail-closed failure mode is the more
dangerous one in practice: a single infrastructure defect becomes a
machine-wide outage of every agent, not a security gap in one call. Fail-open
is the recommendation, on the condition that the live-view tap (§6) is what
makes the failure visible after the fact instead of invisible — which is
exactly why §8's dedup story and §11's open questions matter: fail-open
without a visible signal that it happened is a silently-disabled guard, and
this design treats "make failures observable" as the mitigation for the risk
it is accepting, not a separate nice-to-have.

## 6. Live-view tap

Constraint 2 requires the live-view write to never stall a turn, on any
machine, including one with no web client attached at all. houston already
has the right shape for this, and the generalization preserves it exactly:
`hook.Dispatch` never makes a network call to push state anywhere — it writes
one file, synchronously, in a state directory that the web server reads
independently (Registry → SSE → frontend), decoupled from whether a server
process is even running. There is no live socket on the critical path to
stall on, and no client to wait for a response from.

The router keeps that shape and adds one ordering rule: **produce and print
the consolidated stdout decision for the engine first; write live-view state
second, best-effort, with any write error swallowed exactly the way
`cmdHook` already swallows `Dispatch` errors today.** This ordering is what
makes the tap fire-and-forget in practice, not just in theory — a slow disk,
a full state directory, or a permissions problem on the state file can never
delay the answer the engine is waiting for, because that answer was already
written before the state write is attempted. The generalization is: instead
of one engine's `Event` struct being decoded and written, the router decodes
whichever engine's payload arrived, translates it into the normalized
envelope (§7), runs handlers, emits the consolidated decision, and *then*
writes the same kind of state-dir entry `hook.Dispatch` writes today — same
mechanism, wider input.

## 7. Normalized payload schema

### Inbound: one envelope, translation not reinvention

The six event concepts already line up across engines almost exactly:

| Concept | Claude Code | Codex | Cursor |
|---|---|---|---|
| session start | `SessionStart` | `SessionStart` | `sessionStart` |
| prompt submit | `UserPromptSubmit` | `UserPromptSubmit` | `beforeSubmitPrompt` |
| pre tool | `PreToolUse` | `PreToolUse` | `preToolUse` |
| post tool | `PostToolUse` | `PostToolUse` | `postToolUse` |
| pre compact | `PreCompact` | `PreCompact` | `preCompact` |
| turn end | `Stop` | `Stop` | `stop` |

This convergence is what makes the router tractable — it is mostly
translation, not new semantics. But the event *counts* diverge sharply once
you look past those six: Claude Code has roughly 30–33 distinct hook events
(far more than a quick read suggests — `PostToolBatch`, `TeammateIdle`,
`TaskCreated`/`TaskCompleted`, `FileChanged`, `WorktreeCreate`/`WorktreeRemove`,
`PreModelSwitch`/`PostModelSwitch`, `Elicitation`, `PermissionRequest`,
`PostCompact`, `SubagentStart`/`SubagentStop`, `postToolUseFailure`, and
more), Codex has 12 (including a unique `Interrupt`), and Cursor has roughly
21 (including protocol-specific pairs like `beforeShellExecution`/
`afterShellExecution`, `beforeMCPExecution`/`afterMCPExecution`, plus
`afterAgentResponse`, `afterAgentThought`, and tab-completion hooks). This
corrects the task's original framing directly: `PermissionRequest` and
`PostCompact` exist in Claude Code too, not just Codex; `SubagentStart`/
`SubagentStop` exist in all three engines, not just Claude Code;
`postToolUseFailure` exists in Claude Code too, not just Cursor. Of the
original "engine-only" claims, only `Notification` genuinely holds up as
Claude-Code-only.

Field shapes diverge too, in ways the envelope has to reconcile rather than
paper over: the session identifier is called `session_id` (Claude Code),
`conversation_id` (Codex), or `generation_id` (Cursor); working directory is
a single `cwd` string for Claude Code and Codex but a `workspace_roots` array
plus a per-event `cwd` for Cursor; and Cursor splits tool events by protocol
(shell, MCP, file) instead of exposing one generic pre/post-tool-use pair.

**Rule for events: the six converged concepts get one canonical name each**
(`session_start`, `prompt_submit`, `pre_tool`, `post_tool`, `pre_compact`,
`turn_end`). **Everything else is routed under an explicit engine-scoped
name** (e.g. `codex:PermissionRequest`, `cursor:afterAgentThought`) — never
silently dropped, never invented a fake canonical mapping it doesn't have. A
handler subscribes either to a canonical name, which fires across every
engine that has an equivalent, or to an explicit engine-scoped name, which
fires only for that one engine's literal event.

Cursor's protocol-split tool events are the one case that needs an explicit
call, because under a naive reading they look like a fallback case when they
are actually Cursor's *primary* realization of pre/post-tool-use.
**`beforeShellExecution`/`beforeMCPExecution`/`beforeReadFile` and their
`after*` counterparts collapse onto the canonical `pre_tool`/`post_tool`
names**, with an added `protocol` field (`shell` | `mcp` | `file`) in the
envelope recording which native event actually fired. The alternative —
treating them as engine-scoped only — would mean no guard ever sees Cursor's
most important hook moment under a name any cross-engine guard subscribes to,
which defeats the entire cross-engine reuse case this design exists to make.
A guard like `secret-read-guard` cares that a tool is about to run, not which
of six literal event names its engine happens to spell that as.

The envelope itself:

```
{
  "engine":         "claude-code" | "codex" | "cursor",
  "canonical_event": "pre_tool" | "" ,   // "" when this event has no canonical equivalent
  "native_event":    "PreToolUse",       // the engine's own literal event name, always present
  "session_id":      "...",              // normalized from session_id / conversation_id / generation_id
  "cwd":             "...",              // normalized from cwd, or Cursor's per-event cwd
  "protocol":        "shell" | "mcp" | "file" | "",  // Cursor tool-event split; empty elsewhere
  "tool_name":       "...",              // present on pre_tool / post_tool
  "tool_input":      { ... },            // engine-native shape, see handler-compatibility below
  "native": { ... raw, untranslated engine payload ... }
}
```

`native` exists specifically so that engine-only fields (Cursor's
`workspace_roots` array, Codex's own extra fields) are never silently dropped
or invented into a shape they didn't come in — a handler that needs them
reads `native` directly; the top-level fields are the ones every handler can
expect to exist for the events it subscribed to.

### The handler-side compatibility requirement

The cross-engine reuse case in §4 rests entirely on reusing the four
`agent-hooks` guard binaries across all three engines, not just keeping them
working on Claude Code. That requirement forces a specific decision on both
the inbound and outbound schema above, not just a compatibility footnote.

Verified directly: `secret-read-guard.sh` and `git-default-branch-guard.sh`
both read raw Claude Code PreToolUse fields — `.tool_name`,
`.tool_input.file_path` / `.path` / `.command` — via `jq`, abstain via
`[[ -n $tool_name ]] || exit 0` on anything that doesn't look like that
shape, and write Claude Code's raw `hookSpecificOutput.permissionDecision`
directly to stdout. They do not speak a generic envelope or a generic verdict
schema — they speak exactly one dialect, Claude Code's own.

If the router handed these guards the generic-looking envelope sketched
above unchanged, every one of them would read an empty `tool_name` (it's
nested differently, or the top-level field simply isn't spelled that way)
and silently abstain on **every single call, on every engine** — and §5's
fail-open design makes that failure invisible by construction: no deny ever
fires, no error is ever printed, and the guard simply stops protecting
anything. This is exactly the dangerous combination the escalated finding
behind this section is about, and it has to be resolved, not just named.

**Resolution: direction (a). Claude Code's own PreToolUse JSON shape *is* the
handler wire protocol, for all three engines, unmodified.** Concretely, and
scoped precisely to what the claim can actually deliver:

- The envelope is a superset of **the specific fields the two verified guards
  actually read** — `tool_name`, and `tool_input.file_path` / `.path` /
  `.command` / `.pattern` / `.output_mode` — not a literal, field-for-field
  superset of every field in Claude Code's raw hook JSON. Houston's own
  `hook.Event` struct (`hook/hook.go`) also carries `transcript_path` and
  spells the event name `hook_event_name`; the envelope above carries neither
  under those names (it uses `native_event`, and `transcript_path` would only
  be reachable through the `native` passthrough). Neither guard reads either
  field today, so this doesn't break them, but the earlier "strict superset"
  language overstated the claim — it is a superset of the guard-relevant
  fields, not of the raw JSON shape as a whole. If a future guard needs
  `transcript_path` or a literal `hook_event_name`, promote it to a top-level
  envelope field at that point rather than assuming it's already covered.
- **The harder half of this claim is the tool-name mapping itself, and it has
  to be shown working, not just asserted.** Both guards branch on Claude
  Code's own literal tool-name strings (`secret-read-guard.sh`: `case
  $tool_name in Read) ... Grep) ... Bash) ...`; `git-default-branch-guard.sh`:
  `[[ $tool_name == "Bash" ]]`), so the router's translation step has to land
  on those exact strings for a Codex or Cursor event, not merely avoid
  crashing on one. This is not hypothetical to check: aeye's own Codex and
  Cursor adapters already declare hook *matchers* naming each engine's tool
  vocabulary for the equivalent behaviors, which is direct, existing evidence
  for the mapping table this router needs — re-verified directly against
  `adapters/codex/plugin/hooks/hooks.json` and `adapters/cursor/hooks.json`
  in aeye for this section specifically (this table's source data is not
  part of §1's original grounding pass, which covered aeye's event names and
  script-diff line counts but not its tool-name matcher strings):

  | Native tool identifier | Engine | → Claude-Code-shaped `tool_name` |
  |---|---|---|
  | `Bash` | Codex | `Bash` (already identical — no mapping needed) |
  | `apply_patch` | Codex | `Write` (Codex's file-write mechanism; exact sub-tool, e.g. `Edit` for partial patches, is unresolved — see below) |
  | `view_image` | Codex | `Read` |
  | `Read` | Cursor | `Read` (already identical) |
  | `Write` | Cursor | `Write` (already identical) |
  | `Shell` | Cursor | `Bash` |

  Two of the six rows need **no translation at all** — Codex already calls
  its shell tool `Bash`, and Cursor already calls its read/write tools `Read`
  and `Write`, matching Claude Code's own vocabulary by coincidence of prior
  convention, not by this design's doing. The remaining three rows are a
  small, enumerable table, not an open-ended free-form mapping problem. What
  is **not yet resolved**, and is listed again in §11 rather than folded into
  this "resolved" claim: whether Codex's single `apply_patch` tool should
  always map to `Write`, or needs to distinguish an edit-in-place case that
  guards might want to treat as `Edit`; and how Cursor's protocol-split
  events (the `protocol` field from the inbound schema above) interact with
  this table when a `shell`-protocol event's tool identifier isn't literally
  `"Shell"`. Both are finite, checkable follow-up items against Codex's and
  Cursor's own hook documentation, not open-ended design risk.
- **The outbound schema is the same reuse.** Rather than inventing a second
  verdict format that handlers must learn, the handler-facing wire protocol
  *is* `hookSpecificOutput.permissionDecision` (+ `permissionDecisionReason`)
  on stdout, or silent exit 0 for abstain — exactly what the four guards
  already emit today. The router's internal `abstain`/`allow`/`deny`/`ask`
  representation (§4) is what the router uses *between* itself and its own
  consolidation logic; at the handler boundary, on the wire, it is Claude
  Code's own shape, for every handler, on every engine. A new handler written
  specifically for this registry gains nothing from inventing a different
  wire format, so it doesn't get one.
- Net effect: **the four existing `agent-hooks` guards run unmodified**
  against this design, on Claude Code, Codex, and Cursor alike, *for the tool
  vocabulary in the table above*. No shim, no migration, no rewrite. This is
  stated as a binding constraint on both schemas above, not a compatibility
  note bolted on afterward — it is *why* the envelope's field names are
  Claude Code's own instead of a fresh generic vocabulary. The remaining
  mapping gaps (`apply_patch`'s exact sub-tool, Cursor's protocol-split tool
  identifiers) are small and enumerable, not evidence the approach is wrong —
  but they are unresolved, and the doc should not claim otherwise.

### Outbound: rendering the consolidated verdict per engine

The router's internal verdict (`abstain` / `allow` / `deny` / `ask` + a
reason string, produced by the deny-wins consolidation in §4) has to become
one native decision per engine:

| Engine | Rendering | Confirmed? |
|---|---|---|
| Claude Code | `hookSpecificOutput.permissionDecision` = `allow`/`deny`/`ask`, `permissionDecisionReason` = reason | Yes — documented field, tri-state including `ask` |
| Codex | Unconfirmed | Only fire-and-forget hooks observed deployed; treated as observe-only per §4 until verified |
| Cursor | `permission` field | Field name confirmed; exact accepted value set (binary vs. tri-state) not confirmed |

**When a guard returns `ask` and the target engine has no equivalent (a
binary allow/deny engine), the router degrades `ask` to `deny`, never to
`allow`.** An `ask` is a request for a human decision the router cannot make
on its own; an engine that can't surface that request synchronously should
not have it silently resolved in the permissive direction. This applies to
Cursor unless and until its `permission` field is confirmed to support a
genuine third state, and it is the deliberately conservative default for any
future engine whose decision shape turns out to be binary.

## 8. Native config emission, registration, and coexistence

### One declarative table, rendered per engine

The registry's source of truth is one table: **guard × event × engine**,
listing which handlers subscribe to which canonical or engine-scoped events,
on which engines, with any per-handler timeout override. At build/install
time, the registry renders that table into each engine's native shape. This
section covers each engine's rendering target and how it coexists with what
already writes there.

**Cursor.** Three independent jq mergers already write `~/.cursor/hooks.json`
today (aeye's `install.sh`, an inline dispatcher-stop block, lazytmux's
`cursor-hooks-install.sh`), each with its own marker-scoped strip and
`jq empty` validation, no shared code between them. This design does **not**
propose replacing them — that stays optional future cleanup, explicitly out
of scope under "no flag day." Instead, the registry's Cursor writer follows
the same idiom the other three already established (marker-scoped block,
strip-then-rewrite, `jq empty` validation before commit) and becomes a
**fourth independent writer on day one**. It doesn't need to know about the
other three's markers, and they don't need to know about its — that is
exactly the property that already lets three unrelated writers coexist
today, and it's why this design doesn't treat "four" as materially different
from "three."

**Codex.** `home/ai/codex/default.nix` never touches `agent-hooks` today —
this is the gap the registry closes. The registry writer appends its own
marker-guarded block to `~/.codex/config.toml`, using the same
sed/heredoc-append mechanism lazytmux already uses for the same file (not a
jq merge — `config.toml` can and does carry substantial hand-edited content,
and templating the whole file would clobber it, which is exactly why
lazytmux doesn't template it either).

**Claude Code.** This is the engine with the most existing writers:
`~/.claude/settings.json` (hand-edited, and separately self-installed into by
`houston hooks install` today), the Nix `--settings` overlay (which deep-merges
object-valued keys like `hooks` with `settings.json`, winning per top-level
key), and plugin `hooks.json` directories loaded via `--plugin-dir` (how
lazytmux's and aeye's Claude Code hooks are actually wired today — likely the
source of the task's original "~15 entries" overcount, which conflated
`default.nix`'s own 11 entries with plugin-sourced ones; re-verified count:
6 of those 11 invoke the four shared guards, `secret-read-guard` three times
across Bash/Read/Grep matchers, the remaining 5 are Claude-Code-only scripts).

This is the one engine where "which surface do we write to" has a real
failure mode, not just a style choice, and it deserves the direct treatment
the risk calls for. `hooks` is one of the object-valued keys that deep-merges
between `settings.json` and the Nix overlay **with the overlay winning per
top-level event key** — not per array entry. If the registry writes a
`PreToolUse` entry into `settings.json` and the Nix overlay *also* declares a
`PreToolUse` entry, the overlay wins outright and silently discards what the
registry wrote, with no error anywhere. Checked directly on this machine:
`~/.claude/settings.json` has no `hooks` key at all today, so `houston hooks
install` has never actually collided with the overlay here — there is no bug
to fix, only a conditional risk to design around before anyone runs its
successor on a Nix-managed machine.

The recommendation: `houston hooks install` is **kept and generalized**, not
superseded — it becomes the same command that also renders the registry's
guard-routed entries into `settings.json`, using the same `Check`/install
machinery that already exists in `hook/install.go`. But it ships with an
explicit operational rule attached, not a silent assumption: on any machine
where Claude Code hooks are Nix-managed (this user's own), the events the
registry wants to own must be added to the Nix overlay's own hook list before
`houston hooks install` is safe to run there — either by having the overlay
source its Claude Code hook list from the same registry table (a follow-up
nix-config change, deliberately out of scope for this PR), or by the overlay
explicitly ceding those event keys. Until that follow-up lands, treat the
Claude Code settings.json path as safe only on non-Nix-managed machines or
during initial onboarding, and flag the Nix-managed case as blocked on that
follow-up rather than quietly shipping a config that Nix will clobber the
first time someone rebuilds.

### Registration interface

**A handler-owning repo declares itself with a small manifest file living in
its own repo, not by houston knowing about it in advance.** Concretely: aeye
(or lazytmux, or dispatcher, or nix-config's own `agent-hooks`) ships a
`hooks.registry.json` (or equivalent) alongside its guard binaries, listing
per handler: an id, the binary's path (a Nix store path once packaged, or a
path resolvable at wiring time), the canonical and/or engine-scoped events it
subscribes to (per §7's rule), which engines it applies to, and an optional
per-handler timeout override under the sub-budget in §4.

houston's registry command — the same `houston hooks` family already
responsible for `install`/`check` — is pointed at a list of these manifest
paths, one per participating repo, supplied the same way nix-config already
wires each repo's hook scripts today: as Nix-supplied paths in each repo's
own home-manager module. The registry merges every manifest it's given into
one guard × event × engine table and renders native config from that merged
table. This keeps the source of truth for "what a handler does and when it
fires" inside the repo that owns the handler — aeye's guard's manifest lives
and versions next to aeye's guard — while houston stays the one place that
knows how to render three different native formats. It mirrors the existing
split exactly: nix-config wires paths, it never owns hook logic; this design
adds one more thing nix-config wires a path to (the manifest), rather than a
new kind of thing nix-config has to understand.

### The dedup / double-firing story

"No flag day" (constraint 5) means the four repos migrate independently *of
each other* — it does not mean a single behavior is meant to run through both
its old wiring and the new registry indefinitely. During the window where a
repo is migrating, though, double-firing is a real, near-term cost, and it
splits into two cases that need different answers.

**Live-view state writes are self-healing by construction.** If, transiently,
both an old direct write into houston's state dir and the new registry's own
state write are active for the same session, they key by the same
correlation rule (§10 — tmux pane id, or `(engine, session_id)` headless) and
land on the same `Delta`-keyed entry. `runs/registry.go`'s per-source merge
already treats a second update to the same key as exactly that — an update,
not a second row. Two writers of the same fact about the same run produce one
Run with the freshest fields, not two Runs. This is the same mechanism that
already prevents `nix-config#236`'s "lists every live agent twice" symptom
from recurring here, provided the correlation key stays consistent — the
original bug's root cause was two *different* keys for one pane, not two
writers of one key, which is exactly the failure mode this design's keying
rule in §10 avoids.

**Side-effecting behaviors are not self-healing, and need atomic cutover.**
Anything that posts a notification, writes to another system, or otherwise
has an effect outside houston's own idempotent state model — dispatcher's
`dispatch-notify.sh` is the clearest example — will fire twice, visibly, if
its old adapter entry and its new registry entry are both live for the same
event. There is no dedup mechanism that makes two independent notifications
collapse into one after the fact. The discipline this design recommends: a
behavior's old entry is removed from its adapter's native hook config in the
**same commit** that adds its new registry-emitted entry — migration is
staggered *across* repos and *across* behaviors within a repo, never *within*
one behavior. Double-firing is then bounded to, at most, the review window of
a single PR migrating a single behavior, not a standing state anyone has to
tolerate for the life of the migration.

## 9. Migration order

The task's working assumption was aeye first, because the triplication there
is worst. Re-running that conclusion against the corrected evidence in §1,
rather than re-affirming it by default: some of the original evidence for
aeye weakens under correction (`diagram-guidance.sh` turns out byte-identical,
not drifted; Cursor's stub is deliberate, not degraded; a `justfile` step
already vendors two shared files, so aeye isn't a completely clean-slate
problem). But the correction also surfaces genuine drift the original count
missed — `session-reset.sh` (21 lines) and each adapter's `lib/shim.sh` (61
lines) — so the net picture is not weaker, just more precisely characterized.
aeye also remains structurally distinct from every other repo: it is the only
one with **three-way** duplication (Claude Code, Codex, Cursor), where
lazytmux and dispatcher are two-way at most, and dispatcher has no Cursor
mechanism to duplicate into in the first place.

The two facts that strengthen most under correction — Codex's zero-guard-path
gap and the settings.json/Nix-overlay collision risk — are real, but they are
severity facts about *which problem matters most*, not migration-order facts
about *which repo is safest to prove a brand-new mechanism on first*. aeye's
hooks are diagram/image/session-continuity conveniences, not security
guards; getting the registry's plumbing wrong there costs a broken diagram
script, not a silently-disabled guard. Proving the mechanism on the
lowest-stakes repo first, before asking the design to close the
higher-stakes Codex gap or touch anything near the settings-collision risk,
is the correct sequencing precisely because those two risks are more
dangerous, not less: they deserve a router that has already been proven
correct once, not a first trial run.

**Recommendation: aeye first, on the corrected evidence, unchanged from the
original working assumption.** lazytmux's Cursor injection is the strong
second candidate, and for a specific reason beyond "it's next in line": it
already proves, in production, the exact coexistence idiom §8 commits this
design to reusing — marker-scoped strip plus `jq empty` validation — as a
*fourth* independent writer, not a rewrite. Migrating it second is how this
design validates that "coexist as one more independent writer" actually
holds up under a real fourth writer, before dispatcher (whose migration
would also need to solve the no-Cursor-mechanism gap from scratch) or the
Codex-gap-closing work is attempted.

## 10. Houston panel

**Reuse `/api/runs` and `/api/runs/stream` and the existing `Run`/`Activity`/
`TrailChip` model. This is not a new endpoint or a new frontend surface.**
`Run` is already documented, in the source, as modeling "a Claude Code,
Codex, Cursor, amp, OpenCode or pi session" — the multi-engine surface is
already the intended shape of this type, not something being bolted on.
`RunCard.tsx` already renders tool/hint/trail chips and blocked/question
state generically. The backend change is generalizing the `hooks` `Source`
(`runs/hooksource.go`) to accept the normalized envelope from §7, tagged by
`Run.Agent`, instead of only Claude Code's raw `Event`.

**Correlation key must match the registry's own existing precedent, not
invent a new one.** `runs/registry.go`'s `Delta.Key` is documented as "the
tmux pane id where there is one," and `hooksource.go` already prefers
`v.TmuxPane` over a session-id-based key when a pane is available. This
design keys the same way: the tmux pane id (read via `$TMUX_PANE`, which
`hook.tmuxCoords()` already reads and is entirely engine-agnostic — it reads
an environment variable, not anything Claude-Code-specific) when present,
falling back to `(engine, session_id)` only for headless sessions with no
pane. Concretely, this generalizes `hooksource.go`'s current hardcoded
`"claude/" + sessionID` fallback into `engine + "/" + sessionID` using the
envelope's own `engine` field. Getting this key wrong is exactly how
`nix-config#236`'s "lists every live agent twice" symptom happens — two
different keys for what is really one pane — and it is also what makes the
dedup story in §8 work, since idempotent merging only helps if both writers
land on the same key in the first place.

**Event set: houston's existing `hook.MustHaveEvents`** — `SessionStart`,
`SessionEnd`, `Notification`, `Stop`, `PreToolUse`, `PostToolUse` — is the
natural baseline the panel keeps consuming, mapped per engine through the
convergence table in §7 (`SessionStart`/`SessionStart`/`sessionStart`,
`Stop`/`Stop`/`stop`, and so on). `Notification` is the one event in that set
confirmed genuinely Claude-Code-only, so whatever panel state it currently
drives (houston's `StatePermission`/blocked handling) needs either an
equivalent trigger on Codex/Cursor or an explicit "this signal doesn't exist
there yet" note — it is not silently assumed to exist cross-engine.

This panel-consumed set is **deliberately narrower** than the full router
event set from §7. `hook.go` already declares `UserPromptSubmit`,
`SubagentStop`, and `PreCompact` as named constants without including them in
`MustHaveEvents` — "routed by the hook layer" and "shown on the panel" are
already two different sets in the existing code, not something this design
introduces. The generalization keeps that distinction rather than flattening
it: every canonical and engine-scoped event from §7 can have a handler and
can reach the router's consolidation logic; only the six-event baseline above
is guaranteed to update a card on the panel.

## 11. Open questions

These are named explicitly, per item, rather than folded silently into the
rest of the document as settled fact:

- **The settings.json / Nix-overlay collision (§8).** Asserted from this
  user's own settings-layering documentation (per-key deep merge, overlay
  wins), not independently runtime-tested against Claude Code's actual merge
  behavior. Confirmed only that no collision exists *today* on this machine
  (`~/.claude/settings.json` has no `hooks` key yet) — the risk is
  conditional on the follow-up nix-config change in §8 not landing before
  someone runs the generalized installer on a Nix-managed machine.
- **The exact native multi-hook consolidation rule, per engine.** Confirmed
  only that Claude Code runs matching hooks in parallel; not confirmed how
  Claude Code itself reconciles disagreeing verdicts among them (inferred
  from exit-code semantics, not documented), and not checked at all for
  Codex or Cursor. This design's own deny-wins rule (§4) is stated as
  independent of whatever each engine does natively, deliberately, because
  that native behavior isn't known.
- **Per-engine deny capability beyond Claude Code (§4).** Codex: no deny path
  has been observed in any hook actually deployed on this machine; treated as
  observe-only until proven otherwise. Cursor: a `permission` output field is
  confirmed to exist; whether it accepts a genuine `ask` state or only
  binary allow/deny is not confirmed.
- **Codex's default hook timeout when an entry declares none (§4).**
  Dispatcher's Codex plugin `hooks.json` declares no `timeout` today, and
  what Codex falls back to in that case was not independently verified.
- **Claude Code publisher license inconsistency in HookBus (§2).** README
  states MIT; GitHub's own license metadata for that specific repository
  reports `NOASSERTION`. Noted as a footnote to the prior-art evaluation, not
  something this design depends on either way.
- **The exact tool-name mapping for `apply_patch` and Cursor's protocol-split
  events (§7).** Codex's `Bash` and `view_image`, and Cursor's `Read`/`Write`/
  `Shell`, already match or trivially map onto Claude Code's own tool
  vocabulary (verified against aeye's own Codex/Cursor hook matchers). Not yet
  resolved: whether Codex's single `apply_patch` tool should always map to
  `Write`, or needs to distinguish an edit-in-place case some guards might
  want to treat as `Edit`; and how a Cursor tool event's literal identifier
  interacts with the `protocol` field when the two don't obviously agree
  (e.g. a `shell`-protocol event whose native tool name isn't exactly
  `"Shell"`). Both are checkable against Codex's and Cursor's own hook
  documentation — finite follow-up verification, not open design risk.
- **The 2.35ms measurement (§2, §4) is for `houston hook <event>`'s
  stdin-to-state-write path, not for the router's actual job.** The router
  additionally forks N guard subprocesses (bash + `jq` each) and consolidates
  their output before printing a decision — a materially different code path
  that hasn't been separately measured. The 4.5s internal deadline is
  generous against either number, so this doesn't change the router-shape
  recommendation in §4, but the doc should not imply the 2.35ms figure was
  measured for full guard fan-out, because it wasn't.
