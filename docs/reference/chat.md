# Chat and answering from Chat

Read when changing the Chat tab, `chat/` readers, chat routes, or the answer/permission-prompt executor.

Moved verbatim from the root `CLAUDE.md`; section headings are unchanged.

## Chat

A run's Chat tab renders the agent's own session transcript as a
conversation. Design and measured per-engine mapping:
`docs/superpowers/specs/2026-09-27-mobile-chat-and-dispatcher-home.md`
(slice 1); what was built: `docs/superpowers/plans/2026-09-27-chat-tab-slice-1.md`.

- **`chat/` is standalone**: it imports only the standard library
  (`chat/boundary_test.go` fails otherwise) so it can move to its own module.
  It speaks ACP `session/update` shapes (`chat.Update`: `user_message_chunk`,
  `agent_message_chunk`, `tool_call`, `tool_call_update`) plus `id`/`seq`/`ts`.
  `chat.For(agent)` picks the reader; claude-code (`"claude"`,
  `"claude-code"`) and `"pi"` have one, so codex and cursor have no Chat tab yet.
  `chat.ToolTitle` mirrors `hook.ToolHint`; `hub/chat_title_test.go` pins them.
- **pi mapping** (`chat/pi.go`): `type:"message"` entries count, with
  roles user/assistant/toolResult; `system` and other roles, and other
  non-message entries (`session`, `session_info`, `model_change`,
  `thinking_level_change`), are dropped. `branch_summary` and `compaction`
  entries become a `user_message_chunk` with `_meta.origin` `pi-branch` /
  `pi-compaction` and the summary as content (a `/tree` switch without a
  summary writes no entry, so no divider). Assistant text →
  `agent_message_chunk` with `_meta.messageId` = the entry id, thinking
  blocks dropped, `toolCall` → `tool_call`; a `toolResult`
  pairs by `toolCallId` (`isError` → failed). `Tool()` builds an edit diff from
  the arguments' `edits[]`; `write` gets none. An `aborted`/`error` assistant
  message's tool calls are emitted `failed` (pi never runs them) and an
  `error` message's `errorMessage` becomes an `Error: …` agent chunk.
- **Readers must be chunking-independent**: reading a file in one call or in
  any number of incremental calls yields the same updates. They consume only
  complete lines, never replace an emitted update, and keep no per-file state
  (safe for concurrent use). That is what makes `seq` = the update's ordinal
  from byte 0: the hub ring (`hub/chat.go`, 500 per session) and a scroll-back
  re-read of the file land on the same seqs, across houston restarts too.
  The ring is built lazily: a session has none until its first chat page,
  stream, epoch or subscribe call, which reads the transcript into it (the
  tool route reads the file directly and builds nothing); from then on the
  hub's 2 s tick maintains it. A late-built ring is identical to
  one built at start, so seqs and epochs are unaffected.
- **Epoch**: every cursor is `<epoch>.<seq>`, epoch = a hash of (session id,
  transcript path, hash of the file's first line, ring generation); the raw
  session id never reaches the wire. The generation bumps when the reader
  reports a reset (the file shrank, or the bytes before the cursor changed —
  `chat.Cursor.Pending` fingerprints them) or the path changes; it restarts at
  0 with houston, which is why the file identity is in the hash. A brand-new
  session whose file has no complete line yet resets once when its first line
  lands. A new session in the same pane is a new run `Session`, hence a new
  epoch.
- **`_meta` keys**: `messageId` (on text chunks and tool calls), `tool` (tool
  name — `title` is the human hint), `origin` (`task-notification`,
  `pi-branch`, `pi-compaction`; rendered as a divider), `subagent` (on the
  Agent/Task call's update). The claude reader
  never sets `phase`: the UI treats a text chunk as commentary when
  `_meta.phase == "commentary"` or a later `tool_call` shares its `messageId`.
  Tool input and output never ride the stream; the tool route serves them.
- **Run → session**: `runs.Run.Session` (`json:"-"`) is set by the hooks layer.
  `caps.chat` is true when the key's hooks layer names a Session whose agent
  has a reader, or its crew layer names one (`engine_session`, see "Project and role") for an engine with a reader (`deriveCaps`); the UI offers the tab from it (no probe), and it
  is the default tab when the route names none (`#/fleet/<id>`), except on a joined dispatcher in dispatcher mode, whose default is the Crew tab (see "Navigation").
- **Routes** (`server/runs_chat.go`, behind the `/api/` auth gate; none touches
  tmux): `GET /api/runs/{id}/chat?before=<seq>&limit=<≤100>` →
  `{epoch, updates, more}`; `GET /api/runs/{id}/chat/stream?after=<epoch>.<seq>`
  → SSE `updates` batches with `id: <epoch>.<last seq>` (`Last-Event-ID` wins
  over `after`, so a native EventSource reconnect resumes with no gap), `reset`
  then EOF on an epoch mismatch, a cursor the ring can't serve, the run's
  Session changing (checked every 2 s), or the session going away; the first pull after every connect always sends an `updates` event, `[]` when nothing is missed, so the UI can tell the catch-up batch from live ticks (only the newest update of the catch-up is marked live and animates, `useRunChat`); an idle
  stream gets a named `ping` event every 25 s (see "Stream liveness");
  `GET /api/runs/{id}/chat/tool/{callId}` → name/input/output/diff, each of
  output/oldText/newText capped at 16 KiB (`truncated`), an input over 16 KiB
  omitted rather than cut (`inputOmitted`, since a cut would no longer be
  JSON); a
  failed call carries its error output and no diff. Ladder: 503 no registry ·
  404 `no such run` · 404 `no chat`.
- **Real-transcript check**: `HOUSTON_SAMPLES=<dir> go test -tags samples ./chat/`
  replays `<dir>/claude-code/*.jsonl` and `<dir>/pi/*.jsonl` and logs counts
  only; it skips when unset. Never commit transcript content — fixtures under `chat/testdata/` are
  hand-written. `go run -tags tools ./cmd/sessionlog <file>` prints a file as
  ACP JSONL for eyeballing.


### Answering from Chat

Claude runs only (`run.agent` `claude`/`claude-code`; `isClaudeAgent` on both sides). On another engine's live run the card stays read-only with "answer in the Terminal tab". Code: `answer/` (pure text in, keys out), `server/runs_answer.go`, `ui/src/api/answer.ts`, `QuestionCard.tsx` (wraps `QuestionWizard.tsx`) + `questionStage.ts`, `PermissionBar.tsx`. Design, evidence and frame names: `docs/superpowers/specs/2026-11-01-chat-question-wizard.md`.

- **Question wizard** (`QuestionWizard.tsx`, rendered by `QuestionCard.tsx` for a pending `AskUserQuestion` on a live Claude run with a terminal): a step-by-step flow driven by the pane, not a form sent in one request. The pane is the source of truth, and the wizard renders from `state.questions` (the server's own parse of the call, previews omitted), so it has no 16 KiB cap and sends only indexes into that list.
  - **State**: the card posts `state` on mount and re-reads it every 2 s while idle (no request in flight) and the page is visible, so a change made in the Terminal shows up in Chat. A poll reporting another step or review moves the card; a poll on the same step updates the selection only if the user has not touched that step since it was shown; a failed poll keeps the last state. If `state` fails on mount (404, 503) the card shows the questions read-only from the tool detail (if available) with the Terminal link and keeps polling.
  - **Step screen**: progress "N of M", the headers as chips, the question, radio/checkbox rows, Other (not for a preview-layout question), and a bottom Back / Next row of ≥ 44 px buttons (Back hidden on step 0). Next is enabled when the stage is complete (`questionStage.ts`: single-select is exclusive and never unselects; an option or non-blank Other text, and no Other switched on with blank text) and posts `step`; the last tab's Next leads to review. Single-select rows are a radiogroup with a roving tabindex (one tab stop, arrow keys move and select; arrowing onto Other keeps focus on the radio, only a tap moves it into the text field). A step opens with the pane-reported selection; if the pane's Other text normalizes equal to the client's remembered text, the client's exact text is shown.
  - **Review screen** (`step == count`): each question with the pane's review string. Tapping a row posts `back` repeatedly, one verified request per tab, until that step. Submit posts `submit` with the strings shown. Success shows "Sent — waiting for Claude", tied to the call status.
  - **Plain screen** (`tabbed:false`: one single-select question): the old picker layout and a "Send answer" button (`.chat-question-send-btn`) that posts `step` index 0; 204 means sent. No Back, no review.
  - **Per-step errors**: a 409 with nothing typed re-reads `state` (a read, never a key) and moves the card to what the pane shows, with "The terminal moved on — nothing was typed". A partial failure stays on the step with "Step N didn't finish — check the Terminal", a Terminal link and Re-check (posts `state`). 429, copy mode, 502/503 and timeouts show their messages with the Terminal link. No request is ever retried automatically.
  - **Tool detail**: `fetchTool` has a 10 s timeout. While the call is pending and the detail failed, the card retries every 3 s (GET only) and shows the fallback with the Terminal link meanwhile; the wizard still renders from `state`. A completed or failed call, or a run that is not live (no terminal, `done`, `failed`), renders read-only. The card calls `onLayout` when its detail loads or the picker appears so the sticky timeline stays pinned.
  - **Mobile**: a typical step (≤ 4 options) fits 390×844 without scrolling.
- **`POST /api/runs/{id}/answer`** (both modes). Body, unknown fields 400, max 64 KiB (413). Kinds: `state`, `step`, `back`, `submit` (each self-contained, the pane is the source of truth) and `{"kind":"choice","ordinal":1..9,"frame":"<64 hex>"}` (permission prompt, unchanged). The whole-wizard `question` kind is removed: a peer still running it answers 400 `unknown answer kind`, which the card shows with the Terminal link. Peer bodies are forwarded verbatim. Same resolution ladder as `/input` (503/404/409/409/409/503, via `runPane`), then body (invalid UTF-8 → 400 before decoding, since `encoding/json` would turn it into U+FFFD), then 422 `only a Claude run can be answered`.

  | Kind | Body | Pane must show (else 409 `prompt changed`, nothing typed) | Keys | Success |
  | --- | --- | --- | --- | --- |
  | `state` | `{kind, toolCallId}` | a tab or review of this call, any cursor | none | 200 state; 404 `no question` when the pane shows none of this call |
  | `step` | `{kind, toolCallId, index, answer:{options, text?}}` | tab `index`, cursor on any row | `Up`×k to row 1 if needed, then that tab's keys only | tabbed: 200 state of the tab it landed on; plain: 204 |
  | `back` | `{kind, toolCallId, index}` | tab `index` (`index` ≥ 1, any cursor) or review when `index` = question count | `Up`×k to row 1 (tabs only), then `Left` | 200 state of tab `index-1` |
  | `submit` | `{kind, toolCallId, review:[string…]}` | review, every box ticked, each answer equal (normalized) to `review[i]`, cursor on either choice | `Up` if on `2. Cancel`, check `1. Submit answers`, then `1` | 204 |

  - **Questions** come from the transcript (`ChatTool` on `toolCallId`), never from the client; the client supplies indexes and text, validated against them. Ladder per kind: 404 `no chat` / `no such tool call`; 400 `tool call is not a question`; 409 `already answered` (transcript says the call finished); 422 unreadable questions, `questions repeat` (two questions with identical normalized text and option rows, since the pane identifies a tab by its text) or more than 8 options on a question.
  - **Validation** (400, never quoting client text): `index` in range; `options` in range and unique; `text` trimmed, ≤ 500 runes, no `Cc` rune and no `✔` (U+2714, the pane's commit mark; `Cf` such as ZWJ and bidi marks is allowed), and must not normalize to the Other placeholder (`Typesomething.` / `Typesomething`, refused on any question, since the pane cannot tell such text from an empty field). Single-select takes exactly one option xor text; multi-select takes any options plus optional text, not neither; a preview question takes one option and no text (422, no Other row). `review` needs exactly `count` strings, each ≤ 2000 runes with no `Cc`.
  - **Cursor normalization**: a step or back starts from wherever the cursor is (`Up` reaches row 1 from anywhere on a tab). `k` is the read cursor row minus one, or n+1 from a multi-select Next/Submit row. After the `Up`s the pane must show row 1 with the tab otherwise unchanged before anything else is typed.
  - **Locking**: `step`, `back` and `submit` hold the per-pane `TryLock` for their whole run (429 when another answer is in progress, no queueing). `state` types nothing and takes no lock, so the card's poll never makes a step answer 429; it logs at Debug (Warn on a capture failure) since the card polls it. A poll during a step may see a mid-step screen, so the UI ignores polls while a request is in flight. Logs carry pane, kind, step count and status, never text, labels or frames.
  - **Statuses**: 200 state; 204 typed and submitted; 400 invalid body/answer/`tool call is not a question`/`unknown answer kind`; 404 `no chat` / `no such tool call` / `no question`; 409 `already answered`, `prompt changed` (first check failed, nothing typed), `pane is in copy mode` (nothing typed), or 409 `{"partial":true}` (a later check mismatched or timed out, the pane entered copy mode, or the request was cancelled, after keys went in); 413; 422 as above; 429; 500 chat read or first-key send failed; 502 `{"partial":true}` a send failed after keys went in; 503 `tmux unavailable` (the first capture or mode probe failed, nothing typed) or 503 `{"partial":true}` (a capture or mode probe failed after keys went in). Partial now means one step: a miss strands at most one tab's keys.
  - **State JSON**: `{"tabbed","step","count","questions":[{"question","header","multiSelect","preview","options":[{"label","description"}]}],"options"?,"text"?,"review"?}`. `tabbed` is `count > 1 || any multiSelect`; `step` is the active tab's index and `step == count` is review; a plain dialog is `tabbed:false, step:0, count:1` with no review; a one-question multi-select is tabbed and has a review. `options` (ascending, 0-based) and `text` are the tab's committed selection as the pane shows it: single-select, the `✔` row or the Other row; multi-select, the ticked boxes and a ticked Other row's text; preview, the `✔` row. A wrapped Other loses its `✔` on re-entry, so it counts as committed when that tab's bar box is ticked, no option row has `✔` and the Other row holds text. `text` joins wrapped lines by one space with the mark removed; `options: []` and no `text` means nothing committed. `review[i]` is the text after `→` for question `i`, wrapped lines joined by one space.
- **Executor** (`typeSteps`): the server captures the pane (`capture-pane -p -e`, 200 lines), reads it with `ReadView` into a `View` (active step, cursor row, committed or ticked options, Other text, review strings, tab-bar boxes, Other line count) and plans from it with `PlanStep`, `PlanBack` or `PlanSubmit`, which return steps of `{Expect, Keys}`. `steps[0].Expect` is "the pane shows exactly this view", checked on the executor's own fresh first capture (else 409 `prompt changed`, nothing typed), so a change between the read and the first key cannot slip through. After every key batch the executor polls (100 ms, 3 s timeout) until the next step's `Expect` passes. A tabbed step or back ends with a keyless **landing** step: an `Expect` with no keys (the next tab on row 1 with this tab's box ticked, review, or tab `index-1` on row 1). `typeSteps` returns the capture and width that passed the last `Expect`, and the 200 state is built from that capture. Before each keyed batch it probes `#{pane_in_mode}` (`PaneInMode`): `capture-pane` shows the live screen under copy mode, so every check would pass while copy mode swallowed the keys; a keyless step has no probe. Any failure (mismatch, timeout, capture or probe error, copy mode, cancel) stops typing; nothing after the last batch is checked. One tmux exec per key, since several keys in one `send-keys` call can be dropped. Key sequences (Claude Code 2.1.293, 2.1.299 and 2.1.310 render these dialogs alike):
  - Cursor prelude, when the view's cursor is not on row 1: `Up`×k, then a check of row 1 against the same view.
  - Single option `k`: digit `k` commits and advances (re-pressing the committed option too), then the landing check. A plain dialog submits with nothing checked after.
  - Preview option `k`: a single-select question where any option has a non-blank `preview` renders side by side (`Question.PreviewLayout`): labels on the left, the focused option's preview box on the right, no description lines, no Other row, an unnumbered `Chat about this` row, a `Notes: press n to add notes` hint. Multi-select ignores previews. Checks compare only the label column (each line cut at the preview box's left border); the preview itself is never compared (it can be clipped), and typed notes fail the check. The digit only moves the cursor, so: digit `k`, check the cursor is on `k`, `Enter`, then as above. Other text on such a question is 422, and the wizard hides the Other row for it (same predicate).
  - Single Other: `Down`×n (n = option count), check the cursor is on Other showing the viewed text; if the field held text, `C-u`×(2·lines+1) and check the placeholder; type the text literally (`send-keys -l --`), check it, `Enter`, then as above. Other is reached with `Down`, never its digit: the field keeps its text after another option is committed, and the digit on such a tab commits that stale text and advances. `C-u` clears one visual line of the field, so a wrapped text needs a press per line; 2·lines+1 also covers a focused field that wraps one line more than the unfocused row, and extra presses on an empty field change nothing.
  - Multi: one digit per box in (ticked ⊕ wanted) (a digit toggles without moving the cursor), check boxes and cursor 1. If the field and the wanted text are both empty: `Down`×(n+1) to Next/Submit. Otherwise `Down`×n, check Other, `C-u`×(2·lines+1) when it held text, check the placeholder, type the text if any, check it, `Down`. Then check the cursor is on Next/Submit with the wanted boxes, `Enter`, then the landing check.
  - Back: `Left`, then tab `index-1` on row 1 (from review too).
  - Submit: check the review against the strings, `Up` if on `2. Cancel` and check `1. Submit answers`, then `1`.
- **Dialog region rule**: checks run only inside the active dialog at the bottom of the pane — the lines after the last `─` rule that is directly followed by a tab bar or `☐`/`☒` header, where only an unindented (column 0) rule line counts, so a `────` line inside an indented command or description cannot move the anchor; the rule must span the pane's full width (`#{pane_width}`, read in the same tmux call as the capture, `tmux.Client.CapturePaneWidth`), so a short column-0 `──` spilled into a command never anchors. A capture with no full-width rule (a dialog taller than the 200 captured lines) holds no dialog: `/prompt` is 404, `state` is 404 `no question`, an answer whose first check sees none is 409 `prompt changed` with nothing typed, and a later step that loses it times out as 409 `{"partial":true}`; an unreadable `#{pane_width}` is a capture failure (503 `tmux unavailable`). This applies to question and permission dialogs alike. A named session (`claude --name`, as the dispatcher launcher starts every dispatcher) keeps its input box's top rule, carrying the name, as the pane's last line under a question dialog (blank rows between): `─…─ <name> ─`, or ` <name, cut with …> ─` when the pane is narrow. Exactly that one line is dropped before the question and review checks, only when it is the capture's last non-blank line and it starts in column 0 (a `─` or one space) and ends in ` ─`; a name it cannot recognise (e.g. one starting with `─`) is not dropped, so the dialog fails closed as 409. Permission dialogs draw no such line. Checks never run against scrollback, which repeats the question in the user's prompt and in earlier answer summaries. Text is compared normalized (`answer.Normalize`: leading `│` dropped, all whitespace deleted; ANSI and OSC 8 are stripped earlier, in `captureLines`) so Claude's hard wrapping cannot matter. The active tab is identified by its question text and rows (hence `questions repeat`), not by tab-bar position. Each option row must be exactly `label+description` or `label+✔+description` (the trailing `✔` marks a committed answer on re-entry; no prefix match; descriptions come from the transcript's tool input); the Other row is the placeholder or free text with an optional `✔`; then the `Chat about this` row and a footer. The tab bar's per-question boxes are read but required clear or ticked only by the landing checks. Footer: after `Chat about this`, 1–4 lines which, normalized and joined, must be one of two pinned shapes. Normal: `Enter to select · <nav>[ · n to add notes][ · Tab to switch questions][ · ctrl+g to edit in <E>] · Esc to cancel`. Vim insert (Other field focused): `-- INSERT -- · Enter to select · <nav>[ · ctrl+g to edit in <E>]`, with no `Esc to cancel` and nothing after. `<nav>` is `Tab/Arrow keys to navigate` or `↑/↓ to navigate`; `<E>` is one editor name with no `·`. Any other footer (e.g. vim `-- NORMAL --`) fails closed. A permission dialog never parses as a question dialog and vice versa.
- **`GET /api/runs/{id}/prompt`** (both modes): the permission-style dialog at the bottom of a Claude run's pane (`answer.PermissionPrompt`: after the last unindented (column 0) full-width `─` rule, a line ending in `?`, consecutive choices `1..m` (2 ≤ m ≤ 9) with exactly one `❯` cursor, then an `Esc to cancel` footer). 200 `{question, choices[], detail (≤ 2 KiB, ending in `… (truncated — open the Terminal tab)` when cut), frame}`; 404 `no prompt`; ladder as above, 422 non-Claude. `frame` is a sha256 of the whole dialog, command included: leading `│` dropped, non-blank lines joined by line breaks, words within a line joined by single spaces (so `rm -rf /tmp/x` and `rm -rf / tmp/x` differ, and a line break that moves changes the frame), and `─`/`╌` runs collapsed to one. A rewrap after a resize therefore also changes the frame, and the UI refetches after the 409. `{"kind":"choice"}` re-captures, requires the same `frame` (else 409 `prompt changed`, nothing typed), 400 `no such choice` past the last choice, probes for copy mode (409 `pane is in copy mode`), and presses the ordinal as one key. The hash covers the command's words and line breaks, so an approval cannot land on a command that differs from the one the user saw. A dialog with `Type something` / `Chat about this` rows is a question dialog, not a permission prompt.
- **`PermissionBar`** (`ui/src/fleet/PermissionBar.tsx`): polls the prompt route every 2 s while the run is Claude, has a terminal and its `state` is `blocked` *or `idle`* — `idle_prompt` demotes a still-open dialog to `idle`, and the route stays the authority on whether one exists. A failed poll keeps the last value; polls never overlap and each times out after 10 s. One tap sends one ordinal with the frame it displayed; success hides that frame until a poll shows none or another, or shows it again after 3 polls that still return it. A 409 shows the notice "The session moved on — refresh" (a ≥44 px dismiss button) and refetches; it lives outside the dialog, so it survives the dialog unmounting, and stays until dismissed, a later answer is sent, or the bar deactivates (the run leaves `blocked`/`idle`). Only polls started after a successful answer count toward the 3-poll re-show; an in-flight poll from before the tap is ignored.
- **`answeredHere`** (`RunQuestion`, `RunStatusStrip.tsx`): `ChatTab.tsx` sets it when the Chat tab already offers the answer (a permission bar is shown, or an answerable `AskUserQuestion` is pending); it hides the Chat header's "Reply in Terminal" button so the two affordances do not compete.
- **UI result handling** (`ui/src/api/answer.ts`: `readQuestionState`, `answerStep`, `answerBack`, `answerSubmit`): 200 → `ok` with the parsed state; 204 → `ok` without one (sent); 404 on `state` → no question on the pane. 409 → `moved` (`partial` from the JSON body), except `pane is in copy mode`, which is an error telling the user to exit copy mode and retry ("The terminal is scrolled back (copy mode) — exit it, then retry"). A non-partial `moved` re-reads `state` and moves the card ("The terminal moved on — nothing was typed"); a 409 `{"partial":true}` leaves the card on its step with "Step N didn't finish — check the Terminal", a Terminal link and Re-check, and nothing is re-sent; a 502/503 `{"partial":true}` shows "may have been partly sent — check the agent before resending" with the Terminal link; other errors show their message with the Terminal link. `state` and `fetchTool` time out after 10 s, answer requests after 15 s (reported as possibly partly sent). Sent state is tied to the call status, so the card unlocks when the status changes.
- **Drift fails closed.** Fixtures are hand-written captures: Claude Code 2.1.293 (`answer/testdata/`), 2.1.299 (`answer/testdata/2.1.299/`, and `answer/testdata/2.1.299-named/` for a named session) and 2.1.310 (`answer/testdata/2.1.310/` in vim editor mode, `answer/testdata/2.1.310-normal/` in normal mode, a named session). 2.1.310 renders these dialogs like 2.1.299; vim editor mode was the drift (the `-- INSERT --` footer once the Other field has focus, which the old `Esc to cancel` footer check rejected). The 2.1.293 and 2.1.299 sets still run as tab-reader, review-reader and named-session tests. A Claude Code UI change that breaks a check answers 409 and types nothing (or stops at the first key batch whose result no longer matches), never guesses. When Claude Code's dialogs change, re-record the fixtures and update the parsers together.
