# Federation (peers)

Read when changing peers, forwarding, or dispatching onto a peer.

Moved verbatim from the root `CLAUDE.md`; section headings are unchanged.

## Federation (peers)

Slice 1 of federation (#310): a houston lists other houstons' agent runs in its own Fleet. Slice 2 (#313): the run-addressed routes for a peer run are forwarded to the peer, which runs every check itself (see "Forwarding"). Slice 3 (#316): dispatch, the repo registry and restart are forwarded to a peer too (see "Dispatch onto a peer"). Package `peer/` (`ParseFlags`, one `peer.Source` per peer); the mirrored runs enter the registry as an ordinary `runs.Source`. With no `-peer` there is no peer goroutine and no dial, and `/api/runs` bodies are unchanged. Works in both modes (see "Modes").

- **Flags** (`peer.ParseFlags`, called in `main.go`; any error is `log.Fatalf("invalid -peer: …")` at startup):
  - `-peer NAME=URL` (repeatable) and `-peer-token-file NAME=PATH` (repeatable, optional). Without the latter the token file is `<status-dir>/peers/NAME.token`. A `-peer-token-file` for an undeclared peer, given twice, or a flag without `NAME=value` is an error.
  - `NAME` matches `^[a-z0-9][a-z0-9-]{0,62}$` (lowercase only, so `B` and `b` cannot be two hosts; no `.` or `/`, which `runs.PeerKey` and `idFor` rely on) and is not `local` (the UI's name for the local group). A repeated NAME or a repeated URL (host compared lowercased) is an error.
  - `URL`: `http` or `https`, absolute, no userinfo, query or fragment; an empty or prefix path (reverse proxy) is kept, the trailing `/` trimmed. `http` is accepted only for `localhost`, a loopback IP, a Tailscale address (`100.64.0.0/10`, `fd7a:115c:a1e0::/48`) or a name ending in `.ts.net`; a bare MagicDNS short name over http is refused (telling it is on the tailnet would need resolving it). That rule only checks the URL text (a `.ts.net` name can resolve through public DNS, a `100.x` address can route off the tailnet), so for an `http` peer `Source.dialPlain` also checks every new connection before a byte is written: the remote address must be loopback, or both remote and local addresses must be tailnet addresses (IPv4-mapped addresses unmapped). Because `100.64.0.0/10` is also RFC 6598 carrier-grade NAT space, an IPv4 tailnet hop additionally needs the local address to be held by a Tailscale interface (`net.Interfaces`, name starting `tailscale` on Linux or `utun` on macOS; `interfaceOf` in `peer/config.go`, a var for tests); a lookup error refuses the hop. So a host whose uplink holds a `100.x` address with tailscaled down is refused. `fd7a:115c:a1e0::/48` is Tailscale-specific and stays address-only, as does loopback. Residual: on macOS another VPN's `utun` interface holding a `100.64/10` address still passes; `https` avoids it. Otherwise the connection is closed and the peer reads `unreachable` with class `insecure`. `https` is unchanged. Errors name the peer and never echo the URL, which could carry userinfo. Startup logs `peer` with name and URL (never the token).
- **Token**: `readToken` reads the file on every dial, so rotation needs no restart. It is trimmed and must be non-empty, ≤ 4 KiB and printable ASCII without spaces. A missing, unreadable or invalid file is not a startup error: that peer reports `unreachable` with error class `token` and keeps retrying, so one bad secret does not take the dashboard down. The error text never holds the token. A peer running `-no-auth` ignores the value, but its entry here still needs some valid token file.
- **Transport and dial**: `GET <url>/api/runs/stream?scope=local` with `Authorization: Bearer <token>` and `Accept: text/event-stream`, on the source's own `http.Transport`: `Proxy: nil` (the default `ProxyFromEnvironment` would hand an http tailnet request, header included, to `HTTP_PROXY`), dial (`Options.DialTimeout`, 10 s), 10 s TLS and response-header (`Options.HeaderTimeout`, 15 s) timeouts, no overall client timeout. Redirects are never followed (`CheckRedirect` → `ErrUseLastResponse`): a 3xx is class `redirect`, so the token cannot go to another URL. Accepted: 200 with `text/event-stream`; 401/403 → `auth`, other status → `http`, other content type → `protocol`.
- **`scope=local`** (`server/runs_api.go` `scopeOf`): `GET /api/runs` and `GET /api/runs/stream` take `?scope=local` and then send only runs with `Host == ""` (snapshot, updates, removals and resync snapshots; a peer run's removal carries its `host`, see below). Absent `scope` is unchanged (every run, peer runs included, which is what the UI reads). Any other or repeated `scope` is 400 `unknown scope`. A peer source always dials with it, so a houston re-exports only its own runs and never the ones it mirrors.
- **Loop guard and self**: a received run with a non-empty `host` (an older peer that ignored `scope=local`) is dropped, so the guard does not rely on the peer honouring the query. The runs stream answers `X-Houston-Instance: <32 hex chars>` (16 random bytes minted per process in `server.New`, not secret); a peer answering with this process's own id is refused as class `self`, so one peer list can be deployed to every host, this one included.
- **Sanitising** (`Source.sanitise`): the peer's run is decoded into `runs.Run`, so `json:"-"` internal fields (`Session`, `CrewSession`, `CrewBus`, `Tmux.Server`) never arrive. A run whose id is longer than 1024 (`maxID`; a windowless crew run's id encodes its bus path and branch) or does not match `^[A-Za-z0-9_-]+$` is dropped. A dropped run (carries a host, invalid id) logs Warn `peer run dropped` with the peer and reason, once per reason per connection. Then `Host = NAME`, `Tmux = nil` (a peer pane id addresses nothing here and would collide with a local pane in Workspace's pane → run join), `Caps` intersected field-wise with `Options.Caps` (what this houston forwards: terminal and chat, reply only in dispatcher mode, never kill; `runs.deriveCaps` takes a peer key's caps from its peer layer), `Stale = false` (the peer's own `Stale` describes its tmux control connection; on this side `Stale` on a peer run means exactly "peer unreachable"), `DraftKey` and `Removed` cleared. State, attention, question, crew, PR and activity are kept as received.
  - **Key and id**: registry key `runs.PeerKey(NAME, id)` = `peer/NAME/<peer id>`, layer `runs.PeerLayer` (`peer`). `idFor` maps it to `peer-NAME.<peer id>` (NAME holds no `.`, so the first `.` splits it); local ids start `pane-`/`sess-`/`crew-`/`key-`, so no id collides with a local one or another peer's. A removal of a peer key carries `Host` (`peerHost(key)`), so the wire says which host it belongs to; a local removal still omits it.
  - **Attention** (`attentionOf` → `peerAttention`): a key with a `peer` layer takes `Attention`/`AttentionNote` from that layer, because the peer composed them from layers this host does not have. needs-you ⟺ blocked still holds: a blocked composed state is `needs-you` with no note, a `needs-you` from the peer on a non-blocked state becomes none; `stuck` and `done` pass through with their note.
- **SSE handling** (`peer/sse.go`, `Source.connect`): `event:`/`data:` lines, a blank line dispatches, several `data:` lines join with `\n`, comments and `id:` are ignored. A line or event body over 32 MiB (`maxLine`, bounding what a peer can make us buffer) → `protocol`; `bufio.Scanner` is not used (its 64 KiB token is too small for a snapshot line). Events: `snapshot` replaces the peer's set (every run upserted fresh, `Gone` for each previously known id it lacks); `update` upserts, or with `removed: true` emits `Gone` for that id (ignored when the id is unknown or the payload carries a `host`); `ping` only counts as liveness; unknown events are ignored; malformed JSON → `protocol`. A peer lists at most `maxPeerRuns` = 2000 runs here: a snapshot keeps its first 2000 distinct ids, an update for a new id past the cap is dropped (known ids still update), and Warn `peer run limit reached` logs once per connection.
  - **Liveness**: nothing read for 60 s (`Options.Silence`; the server pings every 25 s, see "Stream liveness") cancels the request, class `silent`.
  - **Outage**: on any end of a connection, or a failed dial, `markStale` re-emits every known run once per outage with `Stale = true` and `Caps` cleared (a stale run cannot be acted on); they stay listed with their last known values. The next snapshot after a reconnect replaces them fresh and drops the ids it lacks and restores the caps. `Run` returns only when its context is cancelled and emits nothing after that.
  - **Backoff**: 1 s doubling to a 30 s cap, ±20 % jitter, reset to 1 s by a connection that got a snapshot.
- **Forwarding** (`peer/forward.go`, `server/peer_forward.go`): a run id `peer-NAME.<peer id>` on a forwarded route goes to peer NAME at `/api/runs/<peer id>/<route>`, with the peer source's own transport (no proxy, no redirect, the `http` hop check), its token (re-read per request) and its bearer header. The peer runs the usual ladder (`runPane`, the answer frame check, the chat ladder); this houston does no pane or session check for a peer run. A houston with no `-peer`, and every local id, behaves as before; a `peer-` id with no such peer is `404 no such run`. Forwarding needs auth: under `-no-auth` every `peer-` id on a forwarded route is `403 peer actions need auth` with no upstream request, and `forwardCaps` grants no cap, so a peer run offers no Chat or Terminal tab; in dispatcher mode a peer dispatcher's Crew tab is still offered (`offeredTabs` does not read caps), and its feed, reply and restart answer 403 `peer actions need auth`, as does every `/api/hosts/{host}/…` route the Dispatch tab and "Dispatch here" reach (anyone reaching this houston would otherwise act on the peer with the peer's token). `GET /api/hosts` itself is not gated, so peers still list in the host picker.
  - **Routes**: terminal (WS), input, answer, prompt, chat, chat/stream (SSE), chat/tool/{callId}; in dispatcher mode also reply, crew/feed and crew/feed/stream (SSE). Each is registered as `peerOr(forward, local)`: a `peer-` id diverts to the forwarder before `findRun`, anything else reaches the local handler unchanged. In tmux mode reply and crew feed stay unregistered (404 for every id, peer ids included) and `Reply` is not a forwardable cap. `restart` (dispatcher mode) is forwarded too, with its `run_id` mapped (see "Dispatch onto a peer"). A tmux-mode peer has no reply or crew-feed routes; they are forwarded anyway and its 404 is relayed.
  - **Target resolution** (a local 404 before any dial): the id splits at the first `.` into NAME and peer id (missing `.`, empty part or unknown NAME is `no such run`); the peer id must pass `peer.ValidID` (`^[A-Za-z0-9_-]+$`, ≤ 1024 bytes); the registry must list a run with that id and `Host == NAME` (so only ids the peer itself published reach it; 503 `run registry not started` when absent). A `chat/tool` call id must be non-empty, ≤ 1024 bytes, not `.`/`..`, with no `/`, `\`, `%` or control rune (else `no such tool call`) and is sent path-escaped. The upstream path is `<peer URL>/api/runs/<peer id>/<constant suffix>`, never built from the request path.
  - **Allowlists**: the request is built from scratch, never cloned. Method fixed per route; only the route's query keys (`before`, `limit` for chat and crew feed; `after` for chat stream; `after`, `from` for crew feed stream), re-encoded; headers only `Content-Type` (POST) and `Last-Event-ID` (streams), plus `Accept: text/event-stream` on streams. The browser's `Cookie`, `Authorization`, `Origin`, `Host` and `?token=` never go upstream. A response carries only status, body and a filtered `Content-Type`: the peer's when its media type is `application/json` or `text/plain` (params kept), else `text/plain; charset=utf-8`; every relayed response also gets `X-Content-Type-Options: nosniff` and `Content-Security-Policy: default-src 'none'; sandbox`, because the peer's body is served on this origin and a peer's `text/html` would run script that can reach the local `/input`. No `Set-Cookie` or other peer header.
  - **Bodies**: POST bodies are read into memory with `http.MaxBytesReader` at the local route's limit (input 50 MiB, answer and reply 64 KiB); over it is a local `413 request body too large` with no upstream request. `peer.Source.Do` takes `body []byte`. `input`'s image payload is inline base64 (`imageUpload.Data`), so the peer decodes it and stores it on its own filesystem. Non-stream responses are read up to 16 MiB; over it is `502 peer response too large`.
  - **Status mapping**: a transport error (dial, DNS, TLS, refused, response-header timeout, insecure hop, unreadable or invalid token file, a `Long`/`Detached` ceiling hit before the request was written) → `502 peer unreachable`; only `peer.ErrOutcomeUnknown` (see "Modes") is `504 peer did not answer in time — it may still be running; check Fleet before retrying`, so `Fast` and `Long` routes never answer 504; a 3xx, 401 or 403 → `502 peer refused the request` (a relayed 401 would read as the browser's own auth failure); any other status (404 `no chat`, 409 `{"partial":true}`, 409 `prompt changed`, 429, 503 `tmux unavailable`, 204) is relayed with its body and the filtered `Content-Type` and headers above. Bodies never name the URL, the token or the raw error. Info logs only for POST and WS forwards (peer name and route); GET forwards (prompt polls, chat pages, streams) log at Debug.
  - **SSE relay**: the upstream GET uses the request context (browser gone cancels upstream); a non-200 maps as above, a 200 with another content type is `502 peer refused the request`; a 200 `text/event-stream` (answered with `X-Content-Type-Options: nosniff`) is copied through 32 KiB reads with a flush each, so the peer's `id:` lines, `reset` and 25 s `ping` pass through and `Last-Event-ID` resume and stream liveness work unchanged. The relay ends when either side ends.
  - **WS relay** (terminal): the target is resolved and `DialTerminal` (same dial as the runs stream, `Authorization` only, no `Origin`; `ws`/`wss` by the peer URL scheme, 10 s handshake timeout) runs before the browser is upgraded, so a failed handshake is a plain HTTP answer like the local route's pre-upgrade 409/503 (peer response relayed as above, transport failure `502 peer unreachable`, a peer answer below 300 such as a 2xx without an upgrade `502 peer refused the request`). A request that is not a WebSocket upgrade is `400 not a websocket request` with no dial. Then the browser is upgraded with the usual Origin check and two pumps copy frames with their type preserved (read limits 8 MiB from the browser, 32 MiB from the peer). Browser-hop liveness mirrors `servePane`: a ping every 30 s, a 45 s read deadline refreshed by the pong and every read, a 10 s write deadline on every write, one mutex per connection for writes. The peer hop is read under the same 45 s deadline, refreshed by every read and by the peer's own pings (its `servePane` pings every 30 s); the relay's ping handler answers each peer ping with a pong through that hop's write mutex. A deadline expiry or failed ping ends the pump and closes both hops, so an abandoned phone socket never leaks a relay or a live peer pane socket. A `CloseError` with a sendable code (not 1005/1006/1015) read from one side is written to the other with the same code and text (4409 and 1011 reach the browser unchanged); any other read error closes the other side with no close frame (the browser sees 1006 and reconnects).
- **Dispatch onto a peer** (slice 3, #316; `server/peer_forward.go`, `peer.Source.DoAPI`): the Dispatch tab starts workers and dispatchers, manages the repo registry and restarts dispatchers on a peer. Dispatcher mode only, registered whether or not `-peer` is given (with no peers every host is `404 no such host`); in tmux mode the host routes are unregistered, so a tmux-mode houston cannot dispatch onto a peer. Same forwarder as above: transport, token, header and query allowlists, body caps (`413` before any dial), relay rules, modes and status mapping; Info log for POST/DELETE, Debug for GET. A tmux-mode peer answers 404 for every route and it is relayed; the UI shows "Dispatch isn't available on <host>." for a peer options 404.
  - **Routes** (`peerRoute` values in `server/peer_forward.go`):

    | here | peer | body cap | mode |
    |---|---|---|---|
    | `GET /api/hosts/{host}/dispatch/options` | `GET /api/dispatch/options` | - | `Long` |
    | `POST /api/hosts/{host}/dispatch` | `POST /api/dispatch` | 256 KiB | `Detached` |
    | `POST /api/hosts/{host}/dispatch/dispatcher` | `POST /api/dispatch/dispatcher` | 256 KiB | `Detached`, `run_id` mapped |
    | `GET\|POST\|DELETE /api/hosts/{host}/repos` | `/api/repos` | 4 KiB (POST/DELETE) | `Long` |
    | `GET /api/hosts/{host}/repos/candidates` | `GET /api/repos/candidates` | - (query `q` only) | `Long` |
    | `POST /api/runs/peer-NAME.<id>/restart` | `POST /api/runs/<id>/restart` | 256 KiB | `Detached`, `run_id` mapped |

  - **Addressing**: a path prefix, not `?host=`, so a route left unwired 404s instead of running `dispatch` on this machine. `{host}` is matched exactly against a configured peer name (`local`, another case or an encoded slash is `404 no such host`, no dial) and never reaches the upstream URL: `peer.Source.DoAPI` takes a constant path and accepts only the five API paths above (`errBadPath`, no dial). `-no-auth` answers `403 peer actions need auth` first. Restart reuses the run-addressed ladder (`peerOr`, run must be listed from that peer).
  - **Modes** (`peer.Mode`, the last argument of `Do`/`DoAPI`; `peerRoute.mode`, zero value `Fast`):
    - `Fast`: the source's own client with its response-header timeout (`Options.HeaderTimeout`, 15 s); every run-addressed route except restart.
    - `Long`: `Source.slow`, a `Transport.Clone()` with `ResponseHeaderTimeout = 0` and `DisableKeepAlives` (same dial including the `http` hop check, no proxy, same no-redirect policy). Bounded by the browser request and a fixed ceiling, `Options.LongCeiling` (default 5 min), that also covers reading the body (the context is held until the response body is closed); options and all repo routes.
    - `Detached`: `Long` for a request the peer finishes on its own once it has it (dispatch, dispatcher launch, restart). Once the request has been fully written (`httptrace` `WroteRequest`; keep-alives are off so a stale pooled connection cannot fake it) any failure, a body read error included, is `peer.ErrOutcomeUnknown`. A failure before the write (dial, token, ceiling) is an ordinary error.
  - **Outcome unknown**: `ErrOutcomeUnknown` is the only `504 peer did not answer in time — it may still be running; check Fleet before retrying` (the peer detaches dispatch, so the work may still land). Every other transport failure, `Detached` ones before the write included, stays `502 peer unreachable`.
  - **`run_id` mapping** (`rewriteRunID`, dispatcher launch and restart only), fail closed: one leading UTF-8 BOM is stripped; a JSON-object body's string `run_id` passing `peer.ValidID` becomes `runs.PeerRunID(host, id)` (`peer-NAME.<id>`); any other `run_id` value is removed; a body that does not decode into a JSON object (BOM aside: non-JSON, an array, `null`, nesting past Go's depth limit, which `JSON.parse` would still accept) is replaced by `{"error":"unreadable peer response"}`, status unchanged. It applies whatever the Content-Type, since the UI parses the text as JSON and a raw peer id would address a local run. The worker dispatch response names no run.
  - **UI**: `api/hosts.ts` (`hostAPI(host, path)`: `/api/<path>` for local, else `/api/hosts/<host>/<path>`; `fetchHosts`); every dispatch and repo api call takes an optional host. `submitDispatch`, `submitDispatcher` and `restartDispatcher` never reject: a failed fetch or body read is `{kind: 'failed', status: 0, error: 'network error'}`. The Dispatch tab (`DispatchView`) has a host picker (label "Host"), fed by `GET /api/hosts` on mount and every 30 s (local only, no peer dial; a failed poll keeps the last list). It shows when peers are listed or the current host is not local, is never disabled, and lists `local`, then peers, then the current host if it is not listed, which stays selectable; another `unreachable` peer is disabled and labelled "(unreachable)", while a chosen host that turns unreachable stays selected and submittable (502 `peer unreachable`). Options load only for the chosen host (no fan-out); a stale answer for another host is dropped and the draft title/task is kept. A peer options 404 whose body starts `no such host` reads "Linked host isn't one houston knows."; another peer 404 "Dispatch isn't available on <host>."; any other failure (a 502 included) shows the error plus Retry. Prefs are per host: local keeps `houston-dispatch-prefs`, a peer `houston-dispatch-prefs@<host>`; the worker/dispatcher mode toggle stays in the local key. `RepoPicker` is per host; the registry and remember-on-use are the peer's own.
    - **Results and in-flight**: `DispatchView` owns the worker and dispatcher results, each tagged with the host it was sent to, and one in-flight slot. Both submit buttons are disabled while anything is in flight, whichever host or form (the worker form's text fields only while a worker dispatch is, the dispatcher form's fields while either is); the host select never is. Switching host keeps the results; one for a host other than the current one is labelled `on <host>`. They render outside the options gate and the mode toggle, so a link or switch that unmounts a form cannot hide a result still landing. The dispatcher form unmounts while the new host's options load, so its draft task rows reset on a host switch; `DispatcherForm` holds no outcome, `DispatcherResult` renders it.
  - **Second layer** (the UI does not trust a peer's answer): `runIdFor(host, runId)` (`dispatchForm.ts`; `runId` is `string | undefined`) accepts a returned run id only if it starts with `peer-<host>.` for a peer (for local, only if it does not start with `peer-`). `DispatcherResult`'s Open run (with the result's own host) and `RestartDispatcher`'s navigation and pending mark use it; an unaccepted or missing id means no navigation, and the restart panel closes. The Dispatch result's View issue link renders only for `safeIssueURL` (`^https://github\.com/<owner>/<repo>/issues/<n>$`), for both the response's `issue_url` (a peer's) and the run's `issue.url`.
  - **Links**: `#/dispatch?host=<name>&repo=&crew=`: a link with any of host/repo/crew switches host at once (absent: local), without waiting for `/api/hosts`; that host's options fetch is the authority on an unknown or unreachable one (see the 404 and 502 messages above). Repo and crew apply after those options load, and a crew-only link picks the repo whose `home`, else `crews`, holds the crew. Picking a host by hand abandons a link still waiting on its host's options. "Dispatch here" on a peer dispatcher's Crew tab and a peer orphan `CrewGroupHeader` links `#/dispatch?host=<host>&crew=<crew>` with no repo: the peer's paths are known only once its options load, and fetching them on Fleet render would fan out. A link naming a crew that no repo of that host lists shows `Linked crew isn't listed on <host> — pick one below.` (`resolveInitial`'s `linkCrewUnknown`; the repo-unknown notice wins when both apply).
  - **Residuals**: a peer list naming this host: the mirror refuses it as `self`, so the picker shows it unreachable, but a request forced to it would dispatch locally through loopback with the full local validation. A browser that drops mid-dispatch cancels the forward, but the peer's dispatch (detached) continues and the worker appears in Fleet. iOS Safari unverified.
- **Health and `GET /api/hosts`** (`server/hosts_api.go`, behind the auth gate, registered in both modes): `{"hosts":[{"name","local"?,"health","error"?,"last_seen"?}]}`, local first (`{"name":"local","local":true,"health":"connected"}`), then peers in flag order. `health`: `connecting` until the first attempt resolves, `connected` once a snapshot arrived, `unreachable` after any failure until the next snapshot. `error` is the class of the last failure, one of `token`, `dns`, `refused`, `timeout`, `tls`, `auth`, `redirect`, `http`, `protocol`, `silent`, `closed`, `self`, `insecure`, `other`; `last_seen` is unix seconds of the last event heard (a `ping` included). No URL, no token and no error text is exposed; at Info/Warn level (`peer connected`, `peer unreachable`) logs carry the peer name and the class on a health transition only (not on each retry); with `-debug` every ended connection also logs its raw error (`peer connection ended`), which can include the peer URL (it holds no userinfo) but never the token. The Dispatch tab's host picker reads it (see "Dispatch onto a peer").
- **Local consumers stay local**: `findRun` (every run-addressed route) and `handleWorkspace`'s `buildWorkspace` (via `localRuns`) see only runs with `Host == ""`. The forwarded routes divert `peer-` ids to the forwarder before `findRun`, and every run-addressed route in dispatcher mode is forwarded. This matters beyond caps: `handleRunReply` does not consult caps and would run `crew reply` in the peer run's `Worktree`, a path that may exist locally, so a peer id must never reach a local handler. These are lookups only; the handlers' point-of-use checks are untouched.
- **UI**: a peer run carries `run.host`.
  - `RunCard` and the run-detail header show a host chip (`run-chip host`); the header also shows a `stale` chip for `run.stale`. Fleet already groups and nests by host (`hostOf`: `run.host || 'local'`); the orphan `CrewGroupHeader` shows "Dispatch here" for a peer group as `#/dispatch?host=<host>&crew=<crew>` and does not fetch local options for it (`useCrewRepos` only when local).
  - A peer run's tabs follow its caps like a local run's (`offeredTabs`, `terminalTarget` in `ui/src/fleet/runTabs.ts`; a peer run has no `tmux` ref, so the Terminal tab accepts `run.host` in its place). The Crew tab is offered on a peer dispatcher only when the local mode is `dispatcher` (the forwarded crew feed exists only there) and the run has `role` `dispatcher` and `crew.name`. `RunQuestion` renders `ReplyComposer` only when `run.caps.reply`.
  - `CrewTab` shows "Dispatch here" and Restart for a peer dispatcher too (host link and forwarded restart, see "Dispatch onto a peer"). `CrewFeedList` resolves a feed row's branch to a worker of the same `crew.name`, branch and host as the dispatcher, so a peer feed never links a local worker and vice versa. A `via: crew` question's `ReplyComposer` in `CrewTab` does not check `caps.reply`: the tab exists only in local dispatcher mode, where reply is forwarded (with auth; under `-no-auth` the reply answers 403), and the peer refuses what it cannot deliver.
  - Drafts: a peer run has no `draft_key` (sanitise clears it), so both composers key by the run id `peer-NAME.<id>`.
  - The Dispatch tab's "Open run" after a dispatch (`findDispatchedRun(runs, branch, crew, host)`, `ui/src/fleet/dispatchForm.ts`) matches only runs of the chosen host (local: `!run.host`), so a same-branch run on another host never replaces the worker just started.
  - **Freshness** (`isFresh`, `ui/src/fleet/staleness.ts`; `Freshness` gained optional `stale`/`host`): false for `run.stale && run.host` whatever `updated_at`, so a stale peer run reads like a time-stale local one: listed, muted, never needs-you, never in the header badge, a group's `M need you`, project section counts, or the crew counts line (`bucket` puts a flagged but not fresh run under `ended`). A local transport-stale run (`stale` without `host`) is unchanged and keeps counting, because `ConnectionSource` marks only the tmux control connection while its hooks layer is live. Server-side `Attention` is untouched by staleness.
- **Residuals**: the peer's Host allowlist (see "Security") must accept the name this houston dials, or the peer answers 421 (class `http`); add it with `-hostname` on the peer. A done or failed peer run folds behind All while its peer is down (blocked and running ones stay in Active), and an unflagged running stale peer run still counts as `working` in crew counts. A peer answering 200 without the instance header is not detected as self. A `Fast` forward is bounded by the transport's 15 s response-header timeout; when it fires the dropped connection cancels the peer's request, so a forwarded `answer` may have been partly typed while this side answers `502 peer unreachable` (never 504) and cannot report `{"partial":true}`. After the peer's tmux server restarts, a pane id can name a new agent and a draft keyed by `peer-NAME.<id>` carries over to it (bounded by the 24 h expiry; local runs key by `draft_key`). iOS Safari is unverified (no WebKit on the dev host).
