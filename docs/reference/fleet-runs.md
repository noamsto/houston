# Fleet runs: project, role, attention, crew join

Read when changing run composition, needs-you/attention, the crew-layer pane join, dispatcher nesting or Fleet UI grouping.

Moved verbatim from the root `CLAUDE.md`; section headings are unchanged.

## Project and role (Fleet)

Every run can carry `project` and `role` (`runs/project.go`, `runs/tmuxsource.go`, `runs/crewsource.go`).

- **`project`** is the main repo's name: `git rev-parse --git-common-dir` of the window's `@git_root`, so a linked worktree resolves to its main repo rather than its own directory name. Crew-bus runs derive it from the bus directory (`<common>/crew`) with no extra git call. A window whose `@git_root` no longer exists (a reaped worktree whose window stayed open) gets no `project` from tmux (never the worktree's leaf name; a crew worker takes it from the bus, others fall back in the UI to `repo`, which for them is still the leaf). Hook-only runs (no tmux window) get no `project`; the UI falls back to `repo`, which `repoAndBranch` already strips of the worktree leaf.
- **Preview line** (`Activity.Task`, from lazytmux's `@claude_task`, else the window task; tmux layer, both modes) skips injected turns (`isInjectedTurn`: a crew bus payload — a leading `{`, `Assignment: {` or `Assignment:{`, e.g. the `Assignment: {"final":true}` window task a finished worker keeps; a human prompt opening with `{` is filtered too — or a leading `<tag …>` envelope such as `<agent-message>`, `<task-notification>`, `<system-reminder>`, or `[Request interrupted`). An injected `@claude_task` falls back to the window task, else the card shows its PR or state rather than markup. A human prompt that itself starts with an HTML-like tag is filtered too. pi has no equivalent feed.
- **`role`** is `dispatcher` when the window's `@crew_name` is the literal `dispatcher` (the dispatcher launcher, `adapters/core/dispatcher.sh`, sets it), `worker` for any other non-empty `@crew_name` and for every crew-bus run, and absent for a solo session. A dispatcher started any other way reads as solo. `worker` never overwrites `dispatcher` when layers merge. Tmux mode sets no `role`: the tmux layer ignores `@crew_name` and there is no crew bus.
- Hook-only runs (`runs/hooksource.go`) resolve `project` from the state file's `cwd` via the git common dir, and only when git actually names it — the first non-empty `Project` across layers wins, so a hook `cd` never overrides the tmux layer's.
- **Ghost hook runs:** a hook state file whose pane is missing from a *successful* `ListPaneOptions` is published as `done` (kept in history, `caps.terminal` false); a failed listing never ends anything. Hook activity newer than that verdict marks the session alive elsewhere (another tmux server) and it is never ended again. A hook session that owns no pane (Claude outside tmux, headless) and never sent `SessionEnd` has no listing to prove it gone: it is published `done` once it has shown no sign of life for `panelessIdleAfter` (6h, the same bound as `crewStaleAfter`). Sign of life is `hub.SessionView.SeenAt`, the newest of the hook state's `updated_at` (merged with the mod's activity while live), the newest timestamped transcript event (not the file's mtime: Claude Code appends timestamp-less bookkeeping records to an idle session's transcript), and the Claude mod's newest record, heartbeats included. A pane-less session that keeps writing its transcript, or has a live mod, stays live; any later sign of life revives it (no bookkeeping). Residual: every non-ended state counts, so a pane-less tool call longer than 6h with no live mod (codex and cursor have none, and pi has none unless its extension is loaded) reads `done` until its next hook event.
- `pruneEnded` still removes an ended hook state file `hub.DefaultPruneTTL` (24h) after its last update. A non-ended file is removed only through `Hub.PruneDead`, which the hooks layer calls on its 5s resync for a session it ended on evidence (pane gone or foreign and not revived, or pane-less idle); it removes the file only once `SeenAt` is older than the prune TTL, re-reading the file with the same rewrite race guard, and drops a discovery-seeded session (no file) from memory the same way. An ended pane-less session is also reported to `PruneDead`, so an ended discovery-seeded session (newest transcript event over 12h old) is dropped once `SeenAt` passes the TTL; discovery's window (equal to the TTL) keeps it from being re-seeded, and the next resync emits the hooks layer's `Gone`. The hub alone cannot tell a live session from a dead one, so it used to keep every non-ended file forever and ghost/foreign history grew without bound; the hooks layer's pane verdict can tell, so the hub prunes only what that verdict ended, and only after a day of silence. Residuals: the revived flag is in-process, so after a houston restart a live session on another tmux server that has been idle ≥ 24h is re-ended as foreign and pruned (its next hook write recreates the file, with its turn and since restarted); a session shadowed by a newer one on a live pane key is never built, so it is not pruned until its pane turns foreign or gone.
- **Foreign panes:** tmux pane ids are unique only within one server incarnation and restart at `%0` after a server restart, so a hook state file can name a pane that now belongs to someone else. Every hook event re-reads `$TMUX_PANE` and the server pid from `$TMUX` (no exec) and recomputes the coordinates when they disagree with the file or on `SessionStart`, recording the server pid as `tmux_server`. `runs/hooksource.go` then distrusts a pane whose recorded server differs from the one houston is listing, or whose state predates that server's start time (which covers files written before `tmux_server` existed): the coordinates are dropped before the run is keyed, so it keys off its session id, carries no `Tmux` ref or terminal/reply/kill caps, and is ended into history under the same revive rule as a vanished pane. The server identity rides the same `list-panes -a -F` listing that produces the pane ids (`#{pid}`/`#{start_time}` in `paneOptionsFormat`), so the two can never disagree about which server minted a pane; a failed listing publishes nothing and leaves earlier verdicts standing, and a tmux that cannot expand those fields logs once and falls back to trusting the recorded pane. The same normalize step disowns a session whose hook state is `ended` even when its pane is live and same-server: tmux hands that id to the next occupant the moment the pane is reused, and a session that announced its own end can never prove it is still there, so it too keys off its session id with no `Tmux` ref or terminal/reply/kill caps (#120). `last_message` is cleared by every hook event except `Notification` and `SubagentStop`, and the hub only surfaces it while the state is waiting or permission (`runFromSessionView` publishes it as `Activity.Message` only for a `blocked` run).
- **Point-of-use server check:** the foreign-pane guard above is sound only for the listing it ran against — `HookSource` polls every 5s, so a tmux restart landing right after a successful listing leaves a window where a cached `Tmux` ref still matches the pre-restart server while the new server has already reused the same pane id. `runs.TmuxRef` and `tmux.Pane` both carry the tmux server pid (`Server`, internal only — `json:"-"`, never reaches the runs JSON/SSE API) alongside the pane id, and `server/runs_terminal.go`'s `runPane` re-resolves and compares it on every send/terminal-attach, refusing with 409 when both the run's recorded server and the freshly resolved pane's server are known and disagree. Either side being unknown never refuses on its own — same "unknown ⇒ false" posture as the foreign-pane guard. This closes the race for the run-addressed routes below. An already-open run-route WebSocket re-verifies too: it re-resolves the pane at open and again after every control-client reconnect, gated on the client's generation counter (`server/pane_ws.go`, `tmux.ControlClient.Generation`), and WS input is dropped until that check passes. A gone pane or a different server closes the socket with 4409, which the UI shows as ended without retrying; an unverifiable resolve closes with 1011 instead. Only an unknown server on the resolved pane falls back to trust (unknown ⇒ allow, as in `runPane`). `metaPollLoop`'s `meta` frames stay ungated.
- **Needs-you (`runs/state.go`):** `blocked` is the only state meaning a human must act now — it drives the badge, the sort order, and `NeedsAttention()`. A turn end alone is never `blocked` (a dispatcher parked on its crew bus between worker events is `idle`, shown as `standby` while its crew has unfinished workers, never needs-you; see "Attention"): a hook `waiting` (`Stop`, `idle_prompt`, pi's `agent_settled`, codex/cursor turn ends) maps to `idle` (`FromHookState`), as does a hook `starting` (`SessionStart` — a fresh, `resume` or `clear` session before its first prompt runs nothing; `UserPromptSubmit` moves it to `thinking`; a `compact` SessionStart is recorded as `thinking`, since an automatic compaction fires it mid-turn), and lazytmux's `@claude_status` `done` (written on `Stop`) is `idle` too, while `denied` (the auto-mode classifier's refusal; the turn continues) is `running`. A role-grid `@crew_role` pane is skipped by every layer (tmux/crew since #99, the hooks layer since #143, which gates its `@crew_role` lookup on the same not-foreign test `normalize` uses), so a critic pane never becomes its own card (#111). A grid lead's `@crew_role=lead` marks the worker itself and is not skipped (#179). The only sources of `blocked`:
  - `hook.StatePermission` — a `permission_prompt` or `elicitation_dialog` Notification (the dialog's message is the `Question`), unless the hub heals it from the transcript (see "Dismissed dialogs"). While the Claude mod is live, its fold replaces this state (see "Claude mod"): the `permission` record (the engine's PermissionRequest) makes the run `blocked` about 6 s before the hook path's Notification, and a Notification record arrives with the hook's own Notification.
  - A Claude `PreToolUse` of `AskUserQuestion` (blocks until answered; `PostToolUse` resumes), with a fixed `Question`, also while its own `permission_prompt` Notification has put the hook state in `permission` (the `Tool` stays `AskUserQuestion`; `ask` is ordered before `dialog`), so from the hooks layer only a permission or elicitation dialog for another tool is `dialog`.
  - A turn end whose last assistant text ends in `?`: the hub tracks `SessionView.Asks` (the final line of the last assistant text block, markdown `*`/`_`/`` ` `` trimmed; reset by any later tool_use, tool_result or user text) and `runFromSessionView` turns a hook `waiting` with `Asks` set into `blocked` with `Question{Via: "pane"}`. Applies to engines with a hub transcript reader (Claude, pi). Two edges: a question followed by a closing line ("Let me know.") is missed, and a rhetorical closing question ("Hope that helps — anything else?") is flagged. The transcript tail lags `Stop` by up to 2 s, so the card can read `idle` briefly first; while the mod is live the `Asks` line comes from the tail of its `stop` record's `last`, so the card does not lag. `Activity.Message` is published only for a `blocked` run.
  - tmux `@claude_status waiting` (a permission/elicitation dialog), and a crew `prompt` attention item (the watchdog's interactive prompt, which a human clears at the pane, via `pane`).
  - A crew worker's own `crew status … blocked "<question>"` (a `blocked` item in crew's view, not a watchdog one) is addressed to its dispatcher, so `runs/crewsource.go` (`routeCrewQuestion`) keeps it `running` with no `Question` (the text stays in `Crew.Detail`) while the dispatcher is alive and the blocked episode is younger than `crewDispatcherSilence` (15 min); otherwise it is `blocked` with a `crew` `Question`. Dispatcher alive ⟺ the crew joins its dispatcher pane (`dispatcherLive` over `joinDispatchers`, see "Dispatcher ↔ crew join"); a houston-minted crew (no registered dispatcher), a dispatcher crew reports dead or whose process is not under its pane, and a dispatcher started without the stamp all read as gone, so such a crew's worker questions surface as needs-you at once instead of being held for `crewDispatcherSilence`. The episode start is the view row's `blocked_since` (unix ms, survives a houston restart; crew resets `age_sec` at every re-stamp, so age alone would never let the 15 min elapse). A worker its dispatcher replied to is `answered` in crew's view (with `answered_at`): it maps to running, not needs-you.

    `Question.Kind` (`turn`|`dialog`|`ask`|`crew`, `omitempty`) says what raised the question: `turn` is the `?` turn end, `dialog` a permission/elicitation dialog or crew watchdog `prompt:`, `ask` an `AskUserQuestion`, `crew` a worker's bus question. Chat omits `RunQuestion` for `turn` (the transcript bubble and the `needs you` chip already show it and the composer answers it); the Terminal tab and the RunDetail header keep it, and Chat still shows the other kinds. Kind rides `runSignature` but changes no state, attention or text.

  **Attention.** `Run.Attention` (`needs-you|stuck|done|standby|""`, plus a houston-worded `attention_note`) is computed once in `composeLocked` (`attentionOf`, `runs/registry.go`) from the composed state plus the tmux and crew layers, and rides `runSignature`. Only the crew layer publishes an input `Attention`/`AttentionNote` (its watchdog verdict); `mergeInto` never copies them, so an `Attention` set by any other layer is ignored, except that a peer key (a `peer` layer) instead takes the peer layer's `Attention`/`AttentionNote` (`peerAttention`, `runs/peer.go`; needs-you ⟺ blocked is kept, see "Federation (peers)"). `needs-you` ⟺ `State == blocked`. `stuck`: the composed state, the tmux layer (`@claude_status error`, even when the hooks layer wins `State`) or the crew layer is `failed`, or the crew layer carries a stuck watchdog prefix. The note is the crew layer's own when the crew layer is failed or stuck (empty for a worker's own `failed`, whose reason is in `crew.detail`); otherwise, for a composed or tmux failure, "Its last turn failed — check its terminal.". `done`: the composed state is `review`, or the crew layer is `done`/`pr_open`, taken from the crew layer even when a higher layer's state (hooks `idle` after the worker's final Stop) wins `State`. `standby` (precedence needs-you > stuck > done > standby > none): a `dispatcher` whose composed state is `idle` while its crew has at least one unfinished worker (the internal `CrewRef.LiveWorkers` on its crew layer, below); it wants no human and is never counted as needs-you. A peer key is not recomputed: `peerAttention` passes the peer's own `standby` through. A crew watchdog verdict is liveness bookkeeping; the view carries it as a `prompt`, `stall`, `watchdog` or `dead` attention item. The item's kind decides the state: a `prompt` item blocks with a `pane` `Question`; when a worker has several kinds the first present wins, in the order `prompt`, `dead`, `stall`/`watchdog`, `blocked`. The message's prefix (`runs/crewsource.go`, `watchdogPrefixes`) only picks the wording and whether the run is stuck, and only for the `stall`/`watchdog` kinds. The watchdog's own message is dispatcher-facing and never shown raw, in the run's note or in the Crew tab's attention items: `projectItem`/`itemMessage` (`runs/crewview.go`) replace a `prompt`, `stall`, `watchdog` or `dead` item's message with houston's wording (`prompt` and `dead` items always get a fixed note; for `stall`/`watchdog` a listed prefix gives its note, otherwise `watchdog: <prefix>` when the prefix matches the activity feed's prefix rule, otherwise `watchdog`):

  | item kind (and prefix) | state | attention |
  |---|---|---|
  | `prompt` | `blocked` + `pane` `Question` | needs-you |
  | `dead` | the row's own state | stuck-dead note ("Its engine stopped — the watchdog marked it failed.") |
  | `stall`/`watchdog` with `quota:`, `turn-stall:`, `quiet:`, `stalled:`, `runaway:`, `unread:` or `budget:` | `running` | stuck, with a per-prefix note |
  | `stall`/`watchdog` with `prompt:`, `load:` or an unknown prefix | `running` | none (host-level / unknown: no claim) |

  **UI.** The header badge counts fresh (≤ 1 h) `blocked` runs (`needsYou` in `ui/src/fleet/staleness.ts`): `NeedsAttention()` plus a freshness gate — the same set as `attention === 'needs-you'`, because needs-you ⟺ blocked. A separate amber `M stuck` badge (`stuckCount` in `fleetList.ts`, the Stuck filter's own predicate, so badge and tab agree) shows beside it while any run is stuck, and replaces `all quiet` when nothing needs you; it opens the Stuck filter and is never added to the needs-you count. Filters: Active · Needs you · Stuck · Done · All, on mobile (`FleetView`) one non-wrapping row that scrolls sideways with the Group toggle (accessible name "Group by project") inline at its end, while desktop keeps the full "Group by project" button in the list header; Active/All sort needs-you > stuck > done > rest, each by recency, and a stale one ranks as rest. Stuck and done cards get a calmer border and chip, never the needs-you red; a `standby` dispatcher shows a calm neutral `standby` chip (tooltip "Waiting on its workers — nothing needs you"), is never in the header badge, and is not a ranked bucket (it sorts with the rest); a stale stuck or done card keeps a muted border, chip and note. An **ended** run (`state === 'done'` with no attention: `SessionEnd`, ghost, foreign) leaves Active immediately and is reachable under All, where each section (host, or project when grouped) lists its first 30 ended top-level runs and a "Show N more" button reveals the rest (`historyCap.ts`; needs-you, stuck, live and done-attention runs, groups and the run open in the desktop detail pane are never hidden; header counts stay full); a `done` run that also carries `stuck` attention is not ended, and a crew-`done` worker (attention `done`) stays. A peer run (`host` set) that is `stale` (its peer unreachable) is never fresh, so it is listed and muted but never needs-you (see "Federation (peers)").

  **Residuals.** (With the Claude mod live, a denied or dismissed dialog and an interrupt arrive as `turn.complete`, so no transcript heal runs and the `idle_prompt` residual below does not apply: `idle_prompt` does not hide a dialog the mod still sees. The approved-tool residual below still holds.) After a permission dialog is approved no hook fires until the tool's `PostToolUse`, so a long approved tool reads `blocked` while it runs (lazytmux has the same gap). A Claude too old to send `notification_type` loses its permission flag. A dialog left open past `idle_prompt` reads `idle` (the notification that heals a dismissed dialog cannot tell it from one still on screen). The transcript heal rests on tool bookkeeping from the main transcript, so it can read `idle` for up to one 2 s tick while the hub's tail lags a freshly raised dialog, and a background `Agent`'s own dialog (its calls live in a sidechain transcript) can be healed when the main transcript holds a finished tool of the same name. A foreground subagent's dialog dismissed with "No" is not healed (its `Task` `tool_use` stays unresolved in the main transcript). A `tool-running` state whose later hook events were lost heals (for `AskUserQuestion` only; a lost `PostToolUse` of another tool reads `running` until the next event) to `idle` even if the agent is still mid-turn (the next hook event corrects it), and only once the transcript tail has read the result (up to 2 s). A crew worker whose own turn ends on a `?` reads needs-you even while its earlier crew question is routed to a live dispatcher — intended: a stopped turn can only be resumed at the pane. A crew branch's `done`/`failed` layer is evicted `crewEvictionGrace` (10 min) after its last status, after which a joined pane's card shows its hooks/tmux state and loses `stuck`/`done` attention (except a `CrewFinished` row, whose terminal state is kept; see the finished-worker bullet). A pane-keyed (joined) run is not dropped but reduced to its identity (`identityOnly`: crew id, codename, title, tier/model, project, branch, PR; no state, attention, question, `crew.detail` or timestamps), so a finished worker stays nested under its dispatcher (and in its `N workers` line and Crew roster, bucketed by its hooks/tmux state) for as long as the terminal pane join holds (the pane still listed and untouched since it finished; a new turn in it fails the join and the run is evicted whole); a windowless (`crew/…`-keyed) run is evicted whole. The identity layer keeps `Agent`, so in the one tick after its pane vanishes the key can list briefly with no state (as any crew layer can). A reaped branch is absent from crew's view, so it has no crew layer at once (no grace). A windowless branch (no single joined pane) is also dropped once its newest dispatch/resume/status row is older than `crewStaleAfter` (6 h), unless it is `blocked` after routing (`crewRunAbandoned`, never dropped by age) or its crew's dispatcher is joined on any bus (alive; not counted for a row synthesized from the bus log, see the cross-repo bullet) and the worker spoke last: a branch whose newest dispatch/resume/status row is a dispatch/resume row or a watchdog status (`workerSilent`: the worker never posted after its newest launch, or went silent and only the watchdog spoke; a live worker posts `working` first and re-stamps its status at every seam, so 6 h with only a dispatch or watchdog row as its newest word means it is gone, while a worker that genuinely works 6 h without a status after a watchdog row is dropped too) is dropped after `crewStaleAfter` even with its dispatcher alive; a pane-joined branch is never dropped by age.
- **Crew-layer source (view-sourced state):** the crew layer takes each worker's state, detail, tier/model/title, PR, age and attention from crew's own `overview` view (`crewview/`, one `crew dash --json --view overview --watch` per bus, see `docs/reference/security.md` "Crew actions" for how it is run; `runs/crewview.go` `crewRunsFromView`), not from a fold of the bus log (the old `deltasFromCrewLog` state fold is gone). Kind mapping: `blocked` item → `blocked` + `crew` `Question` (text = the row's detail), `prompt` → `blocked` + `pane` `Question`, `stall`/`watchdog` → `running` with a stuck note by prefix (`watchdogClassOf`), `dead` → the watchdog's stuck-dead attention note (the state is the row's own); the precedence among kinds is the one above. A row with no item takes `FromCrewState(state)`. Only a *local* worker is enriched with identity; local and `remote_worker` rows are routed (`routeCrewQuestion`), `peer` rows are not; the view is the only state source, so a crew whose stream is down, or whose crew is too old for `--view`, shows no crew state (the dispatcher run carries the notice, below). **Roster failures hold the last listed rows:** when the view's `errors[]` say crew's roster failed for the whole bus (`roster: …`) or for one crew (`crew <id>: workers: …`), the crew layer reads that scope's workers and attention items from the last view that listed them instead of the empty roster (no `Gone`; `spliceHeld`, `runs/crewview.go`): ages are shifted so `updated_at` and each item's `since` keep their listed values, the view's crew-scoped (branchless) items stand unless the whole roster failed, and the rows are re-routed every tick (a question surfaces once the dispatcher dies or stays silent). On a per-crew failure the view's `peer`-origin rows and items of that crew stand (crew still lists them through another crew's roster), and only non-peer snapshot rows plus snapshot peer rows missing from the view are spliced back and marked stale. Each held worker is marked `stale` with `crew.view_notice` "crew could not read this crew's roster; showing its last known state" (shown on its Fleet card and Crew tab row); the dispatcher's notice carries the error. A tick with no view keeps the rows but publishes no workers for that bus. A hold lasts at most `crewStaleAfter` (6 h) of crew's own time (`generated_at`) since the rows were listed, after which the crew reads as the view says. Only crews whose dispatcher is live *on that bus* are listed (a live registered dispatcher pid), so an orphan crew (dispatcher gone) shows no crew state until crew's fleet view lands (dispatcher#1579); a worker dispatched into another repo is covered by the cross-repo bullet below.
- **Cross-repo workers (dispatcher in repo A, worker in repo B):** `dispatch` writes the worker's rows on the bus of the repo it works in (B), while the dispatcher's pane and pid are registered under A's crew; B's overview reports none. crew's `overview` view for B therefore omits the crew (verified against the real `crew dash`: only a live `pid` lists a crew), so the worker would get no crew layer, no `crew.name`, and Fleet would render a plain card in B's project section. The join stays per bus (`joinDispatchers` finds the dispatcher on A; `resolvePane` joins the worker's pane on B, since a window's `@git_root` resolves to B's bus). `scan` then bridges the gap: for a crew that has no row in B's view and is not a held roster, and whose dispatcher is joined on a *different* bus (`joinedOn`), it synthesizes the crew's rows from B's bus log (`identityFromCrewLog` status fold, `logWorkers`: dispatch row for title/tier/engine/model/codename; the newest worker status, dispatcher reply, watchdog row, `reap`/`release` for state, detail, PR, `answered`, stuck/prompt items) and feeds them through the same `crewRunsFromView` as view rows, so state, attention and question routing match a same-repo worker. Synthesis runs only on a tick where B's view is usable (`scan` skips a bus with no view first): with B's stream down, or its crew too old for `--view`, the worker shows no crew state, as for a same-repo crew. Like crew's roster it lists only branches with a worker status since their newest dispatch, and drops a `reaped` branch (a `reap` row after a finished state; a `release` row changes nothing). A crew whose dispatcher is live on no bus is untouched (no rows, as before). Liveness for question routing counts a dispatcher joined on any bus (`joinedOn`), so a cross-repo worker's question stays with its dispatcher until `crewDispatcherSilence`. A synthesized row never counts that other-bus dispatcher as keeping a windowless row alive (`crewRunAbandoned`), so a windowless synthesized row that is not `blocked` ages out after `crewStaleAfter` even while its dispatcher lives (a view-listed row with a live dispatcher does not). `crew.home` for a crew named on both buses is the bus whose dispatcher joined (`crewHomes`). The worker's own `project` is still the repo it works in; only Fleet grouping follows the dispatcher. Residual: the fold reads only B's log, so a dispatcher reply written to A's bus is not seen (`answered` missing; the question surfaces after `crewDispatcherSilence`), and a branch name reused by two crews on one bus resolves to the newest.
- **Crew identity from the bus:** what the view does not carry still comes from the bus log, read by `runs/crewidentity.go` (`identityFromCrewLog`, never status state/detail/PR) into an index by branch: session epoch (`s<epoch>` of the newest worker status sender, for the pane join), engine session (`Run.CrewSession`), codename, colour, `crew.sessions`, last activity and `workerSilent` (staleness, below). An index entry whose crew id differs from the view row's crew is ignored.
- **Remote and peer rows:** a view row with origin `remote_worker` or `peer` (a worker on another machine) becomes a crew-layer run keyed `crewremote/<crew>/<branch>`, `role: worker`, `agent` `crew` when the row names no engine, with `Crew.Origin` and `Crew.Host`, no pane, no identity and no Reply cap (`deriveCaps` grants Reply to a crew layer only when its origin is local). A `remote_worker` row goes through the same `routeCrewQuestion` as a local row. A `peer` row reported `blocked` reads `running` here (never needs-you: its own host surfaces it) and carries no question or detail. The blocked-episode start is the row's `blocked_since`, falling back to its status time, then the view's `generated_at`. The registry hides a `crewremote` key while a houston peer layer lists the same (crew, branch) worker (`shadowedLocked`, `crewRemoteKeyOf`), since the peer's own run is richer. `?scope=local` excludes non-local crew rows (they describe another machine, as peer rows do). While the view has remote or peer rows the stream restarts 60 s after its last accepted line, since crew's own cache of the other machine can go stale without the process dying.
- **View notice:** `crew.view_notice` is a human-readable free-text notice on the dispatcher run (a held worker carries the fixed held notice instead, see roster failures above; the internal `unsupported`/`unavailable` states are not on the wire). It starts with the view's status notice when the view is not usable (a crew too old for `--view` or another schema/view; a stream that exited, e.g. crew's stderr line; `crew dash produced no view for <N>s`; `crew view unreadable: …`; `working directory <root> is gone`), then carries the view's `errors[]` filtered per crew (bus-wide ones such as `roster:`/`bus:`, peer/host errors, and that crew's own `crew <id>: …`; other crews' are dropped), joined by `; ` and capped at 300 bytes (`viewNotice`, `runs/crewview.go`). **Staleness:** the last view stays usable until 30 s after its last line once no crew dash process is live; a process counts as live only once it has written a line or within its 120 s start grace, and one with no line past the grace is killed and restarted (notice `crew dash produced no view for <N>s`). After that the view is dropped and the notice reads unavailable; the notice clears when a good view arrives. Three undecodable lines in a row drop the view with `crew view unreadable: …`. A stream whose working directory was removed (a reaped worktree) is re-rooted by `Manager.Ensure` to another existing root of the repo, and shows `working directory <root> is gone` until then. The Crew tab and a unique-notice line in both shells (`FleetView`, `ConsoleShell`, via `crewViewNotices`) show it. Dispatcher runs also carry the crew-scoped attention items that name no branch (`crew.attention`); a worker's own items ride on the worker run. See "Crew actions" in `docs/reference/security.md` for the `action` on an item.
- **Crew-layer pane join:** `runs/crewjoin.go`'s `resolvePane` joins a crew branch (view row, with identity from the bus) to its one candidate pane. A candidate is any pane carrying `@claude_status` (a Claude run) **or** `@agent_screen` (agent-detect's stamp for pi, codex and cursor) **or** a live hook session on the pane (`paneHookViews`, the trusted per-pane view `paneHookSessions` wraps: not foreign, not ended, not a role-grid pane; hookyard-run pi with no `agent-detect` stamps neither option), excluding role-grid panes (any `@crew_role` other than `lead`) and plain shells. When the branch's latest status is terminal (`done`/`failed`; state and status time come from the view row, `generated_at − age_sec`, and only `s<epoch>` and `engine_session` from the bus) it only joins if the pane looks like that same finished session: its own activity epoch — `@claude_status`'s 2nd field if present, else `@agent_screen`'s, else (a hook-only pane) the hook session's `UpdatedAt` — is within `terminalJoinGrace` (5 min) of the terminal status time, and its state word says the session finished (`done`/`idle`/`error` — the `@claude_status` vocabulary; `error` maps to the internal failed state — for a Claude pane, `idle` for `@agent_screen`, hook state `waiting` for a hook-only pane). The grace exists because the worker posts `done` and *then* ends its final turn, so the Stop hook stamps the pane a few seconds later (observed +4s/+13s); an actively working pane (processing, or waiting on a prompt) is a new occupant even inside the window, and an unknown epoch (0) refuses the join. A third condition guards the pane's identity, not just its epoch: the pane's foreground engine — the tty's foreground process-group leader, reached from `#{pane_pid}` (procfs on Linux, `/bin/ps` elsewhere, since houston's service PATH has no `ps`) — must have started within `[s<epoch> − 30s, record ts]`, where `s<epoch>` comes from the latest status record's worker id `worker:<branch>#s<epoch>-<pid>`; an unknown start time or a bare worker id (no `#s<epoch>`) refuses the join. A fourth condition is engine-session identity: when the branch's bus record carries `engine_session` (`Run.CrewSession`, on dispatcher#652 dispatch/resume rows) and the pane's current hook session id is known, the two must match. The pane→session map comes from the hooks layer's own view (`paneHookSessions` over `hub.Snapshot()`, filtered by the same `paneForeign`/ended/role-pane tests), so a `/clear` or `/resume` in the same engine process starts a new session id the process identity can't see and the stale terminal record no longer joins. Either side unknown — an older dispatcher row, codex/cursor's null `engine_session`, or no hook state for the pane — keeps the process-start rule exactly. Residual: the bus row keeps its pre-`/clear` `engine_session` until a `resume` row replaces it, so a worker that cleared mid-run and then finished splits into a fallback bus card plus the hooks card instead of joining.
- **Dispatcher Crew tab (`CrewTab`, #231, #248):** the dispatcher run's detail tab replaces the retired Crews tab: a crew header (repo name, short crew id, counts line, `Dispatch here`: on a local run when `useCrewRepos` resolves the repo, on a peer dispatcher always, as `#/dispatch?host=<host>&crew=<crew>` (no repo, see "Dispatch onto a peer")), the roster, then the activity feed (see "Crew activity feed"). The roster is the crew's workers (same `crew.name` and host; fresh needs-you first, then live, then history, each by recency). Each member row mirrors `crew roster`: `crew.title`, a `tier · engine · model` line (`crew.tier`, `run.agent`, `crew.model`), `crew.detail` (the live phase, clamped, with the run's age), the PR chip, and `N sessions` when `crew.sessions` > 1; a `via: crew` question carries its `ReplyComposer` unless one of its `crew.attention` items already offers a `reply` action (`hasReplyAction`), a `pane` one a hint to answer in the terminal. The tab also shows `crew.view_notice`, the crew-scoped items, and each worker's own `crew.attention` items with their action buttons (`peek`/`nudge`/`reply`/`merge`; merge asks for inline confirmation, reply opens a text field; see `security.md` "Crew actions"). A remote or peer member (`crew.origin` not local) carries a host chip and no composer. `crew.sessions` counts the branch's bus `dispatch` + `resume` rows (`runs/crewidentity.go`). The row border, chip and the counts line (`working · needs you · stuck · done`, then `idle` and `ended` when non-zero) bucket on `run.attention` (`bucket` in `ui/src/fleet/crewsModel.ts`), flags gated on freshness like the Fleet badge (a stale flag counts as `ended`). A run with no attention counts by state: working, `idle`, or `ended` (state `done`), never `done`. An unflagged idle row carries an `idle` chip, and live tool activity outranks `crew.detail` for the phase line only while the run is working.
- **Codename, colour and home repo:** the tmux layer's `@crew_name`/`@crew_color` give `crew.codename`/`crew.color` for a worker with a window and win when present (the field-wise merge keeps the first non-empty, tmux merging first). A worker with no window takes the codename from the view row's `name` (same `^[a-z][a-z0-9-]*$` rule), else from the bus: the branch's last well-formed `dispatch` row (`name` matches `^[a-z][a-z0-9-]*$`, `tmux` matches `^colour[0-9]+$`, the crew CLI's own rule), the colour via `tmuxColorToHex`; no CRC-pool fallback, and a branch with no well-formed row has neither. `crew.home` is the project of the one resolved bus whose log names the crew or whose dispatcher joined (`crewHomes`), set on every worker of that crew whichever bus it reports on; a crew named on several buses with no joined dispatcher, or on none, leaves it unset.
- **Crew-named chat session (#184):** a `dispatch`/`resume` bus row carries `engine_session`, the engine's own session id (a uuid for claude/pi, `null` for codex/cursor, absent on an older dispatcher's rows — all three read as today). The newest such row per branch lands on `Run.CrewSession` (internal) and, when no hooks layer names a `Session`, on the composed `Session`. `deriveCaps` grants `caps.chat` from it when the *bus record's* engine has a chat reader, with no pane identity involved, so the #120 ended-session disown is untouched: a worker whose Claude exited back to the shell keeps its Chat on the worker card. The registry then hides the session-keyed `sess-<id>` history card (`shadowedLocked`) while any other key's crew layer names that session, and shows it again once that layer is gone.
- **Dispatcher ↔ crew join (#248):** the dispatcher run does not know its crew id, so each crew-source tick `runs/crewdispatch.go`'s `joinDispatchers` maps every crew of every resolved bus's `overview` view to its dispatcher pane, from the `dispatcher` object (`where`, `pid`, `pane`, `alive`: crew reads its pid and pane files and probes the pid, houston reads none of them) on the crew's worker rows (`crewview.Worker.Dispatcher`; the rows after `spliceHeld`, so a crew whose roster failed keeps its held rows' dispatcher). Crew C joins pane P when all hold:
  - Crew reports C's dispatcher pane as P, and P is in the tick's listing with an engine status (`@claude_status` or `@agent_screen`) or a live hook session (same trust rules as above), is not a role-grid pane, and its window's `@crew_name` is `dispatcher`.
  - Process: crew's `alive` verdict (else a signal-0 probe of `pid`; EPERM counts) says the dispatcher is alive, and when a pid is reported it is P's `pane_pid` or a descendant (≤ `maxPPIDSteps` = 32 parent hops; procfs on Linux, `/bin/ps` elsewhere). An unknown pane pid or failed parent walk fails closed; no reported pid has no opinion. The old pane-file mtime check against the tmux server start and the pid-recycle slack are crew's to apply now (a pane id reused by a later tmux server names a pane whose process is not the reported pid's ancestor).
  - Several crews on one pane (a dispatcher restarted in the same pane, the old crew still reported): the greater crew id wins.
  - Residuals: crew lists a dispatcher on its crews' worker rows only, so a dispatcher with no worker row yet (nothing dispatched, or its view unavailable/older than dispatcher#1852) gets no crew layer until the first dispatch, and its pane stays with the tmux and hook layers.

  The join emits a crew-layer delta keyed by P carrying only `role: dispatcher`, `crew.name`, the internal `crew.LiveWorkers` (`json:"-"`, read by `attentionOf` straight from the crew layer, not merged) and the internal `Run.CrewBus` (the bus dir, also set on worker layers; `json:"-"`, merged first-non-empty). `LiveWorkers` is counted per crew id by `scan` over the worker rows it lists (`unfinishedWorker`): crew-layer state not empty, `done`, `failed` or `review` (so not `done`/`reaped`/`failed`/`exited`/`pr_open`), after `crewRunAbandoned` drops; it includes workers blocked on a question to their dispatcher, `remote_worker` and `peer` rows, and held (`stale`) rows at their last-known state. A worker with a crew `dead` watchdog item keeps its view state, so a `working` dead worker still counts until crew moves it to failed/exited. The layer is re-emitted every tick, so the dispatcher recomposes as workers finish. It has no `Agent`, so it never lists a run alone: the tmux/hooks layers supply the card, and between a pane vanishing and the next tick the key is unlisted, not a stateless ghost. A worker's own join to P wins the key (debug log). Residual: `crew adopt` after a tmux restart rewrites `pid` but not `pane`, so the stale pane fails the process check and that crew shows as an orphan crew header until it re-registers (a missed join, never a wrong one); a host where the process probe fails (no procfs and no `/bin/ps`) joins no dispatcher that reports a pid (`warnProbeBroken` warns once).
- **Finished worker with an open window (view drops it):** crew's overview omits a `done`/`failed` worker, so a window left open after the finish would show only the tmux layer's card (codename, no `crew.name`, stale hook `thinking`). `scan` reads such a worker from the bus log (`logWorkers`, the same fold as the cross-repo bullet; rows absent from the view, newest status terminal) when `resolvePaneAs` finds exactly one pane: the normal terminal join (activity epoch within `terminalJoinGrace`, process start, engine session), and, only when that refuses, the same join with the state-word rule dropped (`stuckOK`), since the pane's `@claude_status` stays `processing` when the final turn was cut off. Matching is by bus + branch + those identity rules, never by codename (codenames repeat across crews); a pane touched more than `terminalJoinGrace` after the terminal row, or an engine started after it, is a new occupant and does not join. The relaxed join also only accepts a still-working stamp at most `stuckStampSlack` (30 s) after the terminal row, so a follow-up turn stamped later never reads `done`. Both epoch bounds are lifted when the pane's hook session is known to have had no real user prompt since the terminal row (`panePromptFree`: `last_prompt_at`, set only by `UserPromptSubmit`, is at or before the terminal row; a state file from before that field counts only when its last `SessionStart` source is `compact`, a residual: a follow-up typed under the old hook binary after such a compaction joins until a prompt lands under the new one), because Claude Code's idle compaction re-stamps the pane long after `done` (#369); a real prompt after the row still refuses. A crew whose view still lists the finished worker takes the same relaxed join (`scan`, after the strict `resolvePane` refuses a terminal row). An idle compaction also leaves the hook state `waiting`, not `thinking` (`compact_from` records the state `PreCompact` interrupted). Residual: a follow-up begun inside that slack that opens with one long tool call keeps its stamp and reads `done` until the next hook re-stamps it. A pane that needed `stuckOK` marks its row `CrewFinished` (internal): `identityOnly` keeps its terminal state past `crewEvictionGrace`, and `composeLocked` lets the crew layer's `done`/`failed` beat a stale `thinking`/`running`/`compacting` from the pane layers (never `blocked`: needs-you stays exactly `blocked`). The join ends by itself once the pane is reused. No synthesized attention item of a finished-joined row (strict or relaxed) is published to the dispatcher. The worker then carries `crew.name` and nests under its dispatcher (or its orphan crew group) instead of sitting in Active; only a relaxed-join row stays `done` past `crewEvictionGrace`.
- **Fleet nesting (dispatcher mode, `ui/src/fleet/fleetEntries.ts`):** the top level is dispatcher groups, orphan crew groups and other runs. A `DispatcherGroup` is the dispatcher's `RunCard` with its crew's workers (same `crew.name` and host) nested as compact memoized `WorkerRow`s: codename swatch, title (`crew.title`, issue title, branch), `tier · engine · model`, state dot or attention chip, age, PR chip. A worker whose project differs from its group's (a dispatcher's own `projectOf(head)`, an orphan `CrewGroup`'s header project) and is not `unknown` also shows a project chip after the codename and host chip (`WorkerRow` `groupProject`, `title="works in <project>"`, styled like `RunCard`'s project chip), so a cross-repo worker nested under its dispatcher keeps its repo visible; with `groupProject` undefined (a `CrewGroup` with no project) every worker whose project is known shows it. The card's crew line is exact, `N workers · M need you` (live workers whatever the filter, hidden at none), and a dispatcher with a fresh needs-you worker gets a `M need you` badge and ranks with the needs-you group; the global header badge is unchanged (workers counted once). A `CrewGroup` is the orphan form: workers whose `crew.name` matches no dispatcher run in the list (houston-minted or orphaned crews) under a `CrewGroupHeader` with repo, short crew id, counts line and `Dispatch here`; its project is the members' sole project, else the crew's `crew.home`, else none (so a mixed-repo crew is named and filed under its home repo, not `unknown`). Every other run (solo, or role `worker` with no `crew.name`) stays a plain card.
  - Filters apply to members: a group shows when its head or any member matches, only matching members are nested, and the head stays as the container.
  - Ordering: a group's rank is the max over its head and shown members (needs-you > stuck > done > rest, freshness-gated); ties by the head's stable order (dispatcher: `since`, then id; crew group: the crew id's leading unix seconds, newest first, then id). Members sort by the same rank, then stable order.
  - Past `COLLAPSE_OVER` = 6 shown members a group renders `MEMBER_CAP` = 5 plus a `Show N more` toggle; needs-you and stuck rows sort first, so they are hidden only when more than `MEMBER_CAP` of them are shown.
  - A dispatcher with no shown members and no needs-you worker renders as a plain `RunCard` (with its crew line), not a group container.
  - Tmux mode keeps the flat list: `fleetEntries` returns plain run entries unless the mode is `dispatcher`.
- The Fleet list's **Group by project** toggle (`houston-fleet-group-by-project` in localStorage) is off by default: the flat list keeps needs-you-first across all repos, and the project chip is always visible. Grouping by project or host works on top-level entries: a nested group sits under its head's project and host (a crew group under its members' sole project, else `unknown`), a project's dispatchers lead, and section counts are the runs the section holds (head plus shown members, ended runs hidden by the history cap included). The console rail's Crews narrowing lists workers only (the dispatcher now carries `crew.name` too); `narrowToCrew` keeps the crew's dispatcher card, or crew group, as the container of the narrowed list.
